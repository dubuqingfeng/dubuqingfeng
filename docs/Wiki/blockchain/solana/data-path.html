Solana：交易执行与数据路径源码

1. 具体问题与结论​

同一笔交易先出现在 shred、随后出现在 Yellowstone、最后能用 RPC 查到时，业务究竟可以确认什么？答案取决于观察节点、消息类型、所在分叉和确认等级，不能只比较接口名字。

  • shred 是账本数据的传输单元。 在本文最新稳定 Agave 的 Leader 路径中，交易先本地执行，再将记录请求入队；PoH 异步生成 Entry，广播端再编码为 shreds。接收方可以在自己重放之前拿到交易负载，但不能因此知道执行是否成功，更不能判定最终性。Leader 实现、记录队列、广播实现分别证明这些阶段。
  • Geyser 是节点内部通知接口；Yellowstone 是其上的一个服务实现。 账户、交易执行元数据和 slot 状态经过不同路径产生。Yellowstone 的 SubscribeRequest.commitment 明确支持 PROCESSED / CONFIRMED / FINALIZED，确认等级并非 RPC 独有。Geyser 接口、Yellowstone 协议。
  • RPC 要按方法理解。 账户查询从选定 Bank 读状态；交易查询依赖历史索引和保留数据。getAccountInfo 的 minContextSlot 是响应上下文的最低 slot 要求，不是“返回该 slot 的历史账户快照”。账户查询、交易查询。

本文面向索引器、余额监听和交易状态服务。基础概念见交易、地址、程序、PDA和 Token。本篇不提供交易策略或接口延迟排名。

2. 最小心智模型​

对象内容和约束不能由它单独推导的结论
transaction签名和消息；第一签名通常作为交易 ID。消息包含最近区块哈希、账户、指令；v0 还可能通过 ALT 加载账户被接收或被模拟过，不等于已被链上处理
Entrynum_hashes、hash、transactions；PoH 序列中的一个记录，tick Entry 可以没有交易一个 Entry 不是一个 slot，也不是交易执行元数据
shredEntry 序列编码后的数据分片，以及用于纠删恢复的 coding 分片；slot、类型、index 等标识其位置一片 shred 不一定包含完整交易，也不含完整 TransactionStatusMeta
slot调度和账本组织单位；可能跳过，存在父子分叉关系不是交易唯一标识，也不保证该编号有完整区块
Bank某条父链上、某个 slot 的节点本地执行状态视图，持有账户可见祖先、状态缓存等本地 Bank 已提交或已冻结，不等于网络已最终确认
root本地认定的已扎根分叉边界；推进时保留其祖先路径并处理其他分支一个数值较小的 slot 不因此自动属于该 root 的祖先链

Entry 的实际构造见 PohRecorder::record；v4.4.1 的广播端按 BlockComponent 编码，入口为 StandardBroadcastRun::component_to_shreds。除 Entry 外，运行时允许 block markers 时还可包含 header、footer、parent 更新等组件，不能把所有 shred 都解释为交易 Entry。Bank 的创建、冻结、扎根分别见 Bank::new_from_parent、freeze、squash，root 推进还涉及 Votor root 工具。

接口仍暴露 processed / confirmed / finalized，但 v4.4.1 包含 TowerBFT 与 Alpenglow 的迁移分支，不能统一用旧 Tower 锁定规则解释所有运行模式：commitment service、Votor root 路径。

运行模式此版本源码中的 commitment 更新
TowerBFT 路径根据投票锁定和权益聚合更新 confirmed、super-majority root 等缓存；processed 仍不是最终性保证
Alpenglow 路径Notarize 事件更新 processed 对应的 slot；Votor 选择最终化 Bank 为 root 后，Rooted 分支同时更新 highest-confirmed、root 和 highest-super-majority-root；root 工具还发出兼容 RPC 的 optimistically-confirmed 通知

RPC 按 commitment 选 Bank、Yellowstone 按 commitment 分发说明接口怎样使用这些状态，但协议字段本身不能证明某网络启用了哪种共识模式。不要把固定等待毫秒数当作承诺，也不要再写成“所有版本都固定等 31 个区块”。交易失败也可以 finalized：确认的是包含该执行结果的账本，不代表 err == null。

4. 完整主路径：这笔转账如何变成可消费数据​

Leader：执行、记录与广播​

以下是 Agave 基线下普通交易的关键依赖，不是“任何时刻都只有一笔交易”的全局串行流水线。

  1. 客户端通过 RPC sendTransaction 或 TPU 路径送入签名交易。RPC 返回签名只代表接收和提交路径的结果，不能作为已上链证明。Tpu::new_with_client 组装 QUIC 接收、Fetch、SigVerify、BankingStage；调度前后还要检查交易结构、签名、区块哈希、预算、账户锁等。无效或过期交易可能在进入账本前终止。TPU 组装、Consumer。
  2. Consumer 在账户已锁定的 batch 上调用 Bank::try_enter_transaction_execution；获得绑定本 Bank 的 TxExecutionGuard 后才 load/execute。正在退休的 Bank 可以拒绝新执行并返回可重试结果。对于 E1 这种普通转账，执行结果中形成扣款、收款及费用相关状态，此刻尚不是全网最终状态。Consumer、Bank 执行 guard。
  3. 选出 was_processed() 的交易并计算 Entry 字节预算，再取得 freeze_lock，释放执行 guard，为当前 slot 预留 Entry 字节。TransactionRecorder::record_transactions(bank.bank_id(), ...) 计算交易哈希，最终调用 RecordSender::try_send：检查当前 Bank ID、剩余入队预算和通道状态；成功时返回可选的交易起始 index。记录器、记录队列。
  4. Consumer 在记录请求成功入队后即可 commit，不等待 PoH 线程实际生成 Entry。 RecordSender 的明确契约是非阻塞发送；容量预留及 receiver 的关闭、排空逻辑保证正常推进时已接纳记录不被丢弃。如果字节预算或入队失败，Consumer 返回可重试索引，不继续该 batch 的 commit。入队成功只证明本地接纳，不是持久化或全网确认。Consumer、RecordSender / RecordReceiver。
  5. PoH 服务异步消费队列，PohRecorder::record 按 Bank ID 检查当前工作 Bank、混入哈希并构造 Entry，送入有界 working_bank_sender；输出满时阻塞施加背压，不静默丢掉已混入的记录。广播端 process_receive_results → component_to_shreds → make_merkle_shreds_from_component 编码并发送 data/coding shreds；如果启用相应 block markers，还会处理 header 等组件。PoH recorder、广播实现。

第 4、5 步由同一个已接纳的记录请求分出账户提交与 PoH/广播工作，二者可以交错：不能声称“Entry 已生成”才会提交，也不能声称所有账户通知都早于网络广播。TransactionRecorder 仍有一条旧注释写着等待响应，但本版本真实函数体委托给 try_send，应结合记录队列实现理解。因此“远程 shred 比某台 RPC 先看到交易”仍不能推出“远程 shred 捕捉到了 Leader 执行前的意图”。普通交易 Entry 不包含 E1 的完整 TransactionStatusMeta；新版可用 footer 提供 Bank hash 等信息，也不能替代单笔交易元数据。

被处理但指令失败的交易可能被记录，不能把 was_processed() 读成 err == null；但执行 flags 的 drop_on_failure / all_or_nothing 以及 NoOp 等分支会改变处理结果，不可反过来承诺所有失败都会进入账本。Consumer、账户保存分支。

跟随节点：收数据后在自己的 Bank 重放​

网络接收侧先验证 shred 来源和结构，结合修复及纠删恢复补齐可用数据。WindowService::run_insert 调用 Blockstore::insert_shreds_at_location_handle_duplicate 存入本地账本，完成的数据集推动重放；不是按 UDP 到包顺序逐笔执行。WindowService。

ReplayStage::replay_blockstore_into_bank → blockstore_processor::confirm_slot 从 Blockstore 读取并校验数据。v4.4.1 的交易主路径是 process_entries → BankWithScheduler::schedule_transaction_executions → DefaultTaskHandler::handle → runtime::transaction_execution::execute_batch，再执行并提交到本地 Bank；不是旧版的 process_batches 调用链。process_entries 对含交易的 Bank 断言已安装调度器，按账本起始 index 生成 task ID，并由统一调度器处理账户冲突。Blockstore processor、调度入口、默认任务处理器、执行器。

可对已有连续数据增量重放，不要求整个 slot 的最后一片先到。slot 完成后，complete_bank_replay 汇总调度执行与异步验证结果；若运行时允许 block markers，跟随节点还通过 freeze_and_verify_bank_hash 核对 footer 提供的预期 Bank hash。不通过验证的分支可能被标 dead；迁移切换中断等情况有单独处理，不能把所有重放中断都等同于无效交易。ReplayStage。

这里 confirm_slot 是函数名，表示账本校验与处理入口，不是客户端 confirmed commitment 的投票承诺。同一交易在不同节点各自执行，出现 Geyser 通知的时间取决于各自重放进度、队列、插件配置及订阅过滤条件。

Bank 生命周期与提交边界​

Bank::new_from_parent 在父 Bank 上建立新状态视图，通常不是复制一份全量账户数据库；bank_id 由本节点运行期间的生成器分配，不是跨节点共用的链上标识。活动 Bank 接受多批提交；Bank::commit_transactions → Accounts::store_accounts 写入带 slot、Bank ID 及祖先可见性的路径，调用返回不表示 fsync 或成为 root。Bank 提交、账户存储。

freeze 使用与 record 入队/commit 区域协调的 hash 锁，处理费用等延后状态、完成账户 hash 更新并计算 Bank hash；Bank 退休还会通过执行 gate 等待 load/execute 的副作用结束。冻结是单向的本地生命周期变化。随后按运行模式推进共识和 root；squash 将自身及祖先状态扎根，Votor 的 root 工具与 ReplayStage 的命令处理更新账本、BankForks 和 RPC 兼容通知。未胜出的分叉不会因为它曾 freeze 就成为最终状态。Bank::freeze / squash、执行 gate、root 工具、ReplayStage。

账户、交易与 slot 通知​

  • 账户路径：Bank::commit_transactions → collect_accounts_to_store → Accounts::store_accounts 分配 write version，经 AccountsUpdateNotifierImpl::notify_account_update → GeyserPlugin::update_account_for_bank 通知。该版本在调用 AccountsDb::store_accounts_unfrozen 前先发通知，所以回调触发不保证并发 RPC 此刻已能读到新值，更不表示磁盘已落稳。启动恢复另走 update_account_from_snapshot，可没有交易签名与 Bank ID。账户筛选、账户存储顺序、账户通知。
  • 交易路径：Committer 将提交结果、余额和区块内索引送入 TransactionStatusSender，TransactionStatusService::write_transaction_status_batch 组装 TransactionStatusMeta，经 TransactionNotifierImpl::notify_transaction 通知插件；是否持久化 RPC 历史还有单独配置。Committer、TransactionStatusService、交易通知。
  • slot 路径：Agave 的 SlotStatusNotifierImpl 对 processed、confirmed、rooted、created-bank 使用 update_bank_status(..., bank_id)；first-shred、completed 等走 update_slot_status。交易通知最终调用 notify_transaction_for_bank。这些与账户回调、状态服务线程、网络客户端之间没有全局到达顺序。slot 通知、交易通知、配套插件入口。

Yellowstone 将上述新版回调转为内部 Message，再做过滤、批处理、区块重建和客户端分发。其 geyser_loop 的 processed 通道与 block_reconstruction_loop 的 confirmed/finalized、回放管理各有职责。服务实现。SubscribeUpdate.created_at 是服务消息时间；回放路径会重新生成部分 slot 消息的时间，不能据此还原原始执行时刻或直接计算网络延迟。

self.committer.commit_transactions(/* ... */);
drop(freeze_lock);

这解释了预算不足、通道满或 Bank ID 已失效时为什么不能发布“本 Bank 已提交”的业务事件。这里的 record 成功是入队成功；不能据这个返回值宣称 PoH 已经生成 Entry。从源码继续追踪 TransactionRecorder::record → RecordSender::try_send，可看到容量预留和 index 分配；RecordReceiver 的关闭与排空约束负责正常退出此 Bank 时保全已接纳记录。Consumer 260 行起、记录队列。

失败账户的保存逻辑是另一处不能略过的分支：collect_accounts_to_store。

// 阅读摘录：省略参数
if executed_tx.execution_details.status.is_ok() {
    collect_accounts_for_successful_tx(/* ... */);
} else {
    collect_accounts_for_failed_tx(/* rollback_accounts ... */);
}

失败路径保存 fee payer、必要时 nonce 的回滚账户状态，阻止失败指令的普通写入泄漏，同时保留应支付费用及 nonce 相关变化。因此“指令原子失败”不能写成“所有账户和费用都完全不变”。另一方面，早期就被拒绝的交易未必有可查询链上记录，也不能承诺所有失败都扣费。

Yellowstone 的请求类型直接反驳“只有 RPC 能选择确认等级”的说法：完整协议。

enum CommitmentLevel {
  PROCESSED = 0;
  CONFIRMED = 1;
  FINALIZED = 2;
}
// SubscribeRequest 内：
optional CommitmentLevel commitment = 6;
optional uint64 from_slot = 11;

字段存在不代表无限回放。在本固定版本中，只有流的首个订阅请求可以指定 from_slot 触发回放，后续请求中的该字段会被忽略；请求启动快照的订阅也不执行这一路回放。服务必须启用 replay_stored_slots，消费者还须处理保存窗口和背压边界。GrpcService::client_loop / client_loop_replay 的具体错误如下：

条件gRPC 状态与消息消费者处理

这些错误不能统称为 UNAVAILABLE；该版本另在服务关闭等路径返回 UNAVAILABLE。回放与实时流的衔接有服务端去重逻辑，但消费者仍须按自己的持久化边界实现幂等恢复。

6. 失败、去重与恢复​

按数据类型建立身份​

下面是消费端的工程建议，不是协议承诺的“恰好一次”。source_epoch 表示消费者给某个节点运行实例分配的来源代号；节点重启、切换提供商时重新分配，避免把本地计数器误作全网 ID。

数据建议保存的观察身份重复或冲突的处理
shred网络身份、slot、shred type、index，以及 payload hash / 签名证据相同位置相同 payload 可去重；同位置不同 payload 是冲突证据，不能直接丢弃。FEC set 辅助恢复，不能把 coding shred 当交易
Entry来源与分叉身份、slot、Entry index、Entry hash去重后再维护交易起始索引；缺片时保留缺口，不假造空 Entry
交易观察网络、来源实例、bank_id（若提供）、slot、signature；保留 index 和后续 blockhash同签名的多次观察更新确认状态；不能把不同分叉上的同签名覆盖成唯一成功。最终业务入账可以按 canonical signature 幂等，但必须先验证所在最终链及 err
账户写入来源实例、slot、bank_id（若提供）、pubkey、write_version同账户同 slot 多写要保留；同一 Bank 内用 write_version 处理乱序。该数值不用于跨节点比较新旧，不作为永久全局序号
slot 状态来源实例、slot、可选 bank_id、status不用 max(slot) 代替状态机。维护 parent、dead 与最终链信息；单条 processed 通知不能清除其他分支

write version 的分配范围与启动恢复的独立通知路径可从 Accounts::store_accounts 和 snapshot 恢复通知核验；新版协议显式提供 Bank 身份，FIRST_SHRED_RECEIVED 与 COMPLETED 没有 Bank 归属。没有 bank_id 的旧服务或缺少 blockhash 的消息，不能可靠区分所有同 slot 的 Bank 实例：应将其保留为来源相关的暂态观察，等区块证据或最终账户快照对账，不凭空发明分叉标识。

交易和账户怎样关联​

E1 的交易 ID 可以连接 getTransaction、状态查询与区块签名列表。若消费 Geyser，账户消息的 txn_signature 非空时，可按同来源实例、同 Bank、同 slot、同签名 join 交易事件；账户事件可能先到，必须允许两侧暂存。txn_signature 为空时不能把“同 slot 最近到达的交易”硬配给它：启动快照、Bank 初始化及其他非交易更新都可能没有关联签名。账户转换与快照路径、新版账户回调。

slot 结束也不代表一个过滤订阅拿到了该 slot 的所有交易或账户。getTransaction.meta 有余额、日志、Token 余额等信息，但不包含所有账户任意时刻的完整二进制数据。重建账户历史需要从已知快照持续采集完整的写入、处理分叉，或自行重放账本；只有交易历史 API 不够。

检查点、重连与回填​

建议把业务状态分为可撤回的 tentative 和已核对最终链的 finalized 两层，按以下顺序恢复：

  1. 先落盘再确认检查点。 原始事件、去重身份、业务更新及消费进度在同一存储事务中提交；否则进度领先会丢数据，进度落后会导致重复，后者必须能幂等处理。分别保存实时接收高水位与“目标过滤范围内已核对完整”的 finalized 检查点，附网络 genesis hash、slot、blockhash、订阅过滤条件及版本。
  2. 断线重连从重叠范围开始。 该 Yellowstone 版本有 from_slot，但受服务配置和窗口限制；不要假定跨提供商保留窗口相同，也不要从“最后收到 slot + 1”开始以致漏掉同 slot 尾部。重叠窗口本来就会带来重复，必须按上表幂等合并。回放与 live 交界处理。
  3. 显式处理落后和队列溢出。 回放不支持、请求早于窗口、客户端消费滞后都不能当作“无新数据”。记录 gap，保留实时流缓冲，再用 RPC 的 getBlocks / getBlock 对最终链区间核对交易。先辨明跳过 slot、数据裁剪和接口失败，不能把每个缺失编号都称为数据丢失。归档能力不足则保留无法补齐的区间并报警。
  4. 账户恢复另做设计。 如果缺失的是账户写入，仅查回区块交易不能恢复每次写入的完整 data。如果业务只需要某组账户的当前最终状态，可以先开启订阅并缓冲，再拉取带 context.slot 的账户快照，丢弃已被快照覆盖且可证明属于同一最终链的增量，再继续应用后续写入；跨分叉或无全局可比 write version 时要重新查询对账。多批账户快照不保证同一上下文，更不能当作全网原子快照。需要精确历史则使用已有快照加完整变更日志，或搭建可重放的状态存储。
  5. 分叉失效要撤回派生结果。 将 dead / 落败分支的 tentative 事件标为失效，撤销对应派生余额、提醒等可逆状态；最终入账以规范链核对结果为准。不能只删除 raw event 却保留它带来的汇总。并非每个提供商都保证为所有落败分叉发送完整撤销流，最终 root/区块链路对账不可省略。

这些设计要按业务选择：余额面板可展示带确认标签的暂态结果；不可逆结算通常应等 finalized 且 err == null 后入账。过滤条件改变相当于改变数据集，旧检查点不能直接证明新数据集完整。

RPC 历史与常见误判​

7. 最小复现实验​

E1：无需钱包的同签名只读对账（已执行）​

环境：macOS 26.5.2 arm64，Python 3.14.2 标准库，无 SDK、无付费服务、无私钥。2026-11-19 13:11:09–13:11:12 UTC 执行；以 JSON 中每个请求的实际时间为准。端点 https://api.devnet.solana.com，getGenesisHash 返回 EtWTRABZaYq6iMfeYKouRu166VU2xqa1wcaWoxPkrZBG。RPC 自报版本见前文，不能把它等同于阅读源码基线。

脚本下载：observe_transaction.py。在仓库根目录执行：

python3 wiki/static/examples/solana/observe_transaction.py \
  --rpc https://api.devnet.solana.com \
  --signature 3pePAiDRXjEhE85sZxzu6ydr3V3RxfgqvwkYr2bPxFYoZj2jbuKCY2wpV3yF9E6tbL59GzR5SwPsQXtxXzzQjEZE \
  --max-version 1 \
  --output /tmp/solana-observation.json

脚本依次调用 getGenesisHash → getVersion → getTransaction(finalized, jsonParsed) → getSignatureStatuses(searchTransactionHistory=true) → getBlock(signatures) → getMultipleAccounts(finalized, minContextSlot=交易slot)；验证返回签名、slot 和错误状态相符，再输出区块位置与余额差。超时、RPC 错误、缺少数据、版本不支持都会退出非零，并将已完成的交换及失败原因保存到输出文件。它不实现未知版本交易的二进制解码；--max-version 1 仅声明允许 RPC 返回的上限，本次选中的交易仍是 legacy。

实际终端输出摘录如下；完整的四个账户余额见原始证据：

{
  "slot": 524001628,
  "blockhash": "HFKNVzC4J3ZonZcev4Rzu468jTBZkLexV32L9PpmUgS8",
  "parent_slot": 524001627,
  "transaction_index": 24,
  "transaction_version": "legacy",
  "err": null,
  "confirmation_status": "finalized",
  "fee_lamports": 6000,
  "compute_units_consumed": 450,

  "current_accounts_context_slot": 524001883,
  "current_accounts_are_transaction_snapshot": false
}

发现样本时，getBlock 对当时最新 finalized slot 使用 maxSupportedTransactionVersion: 0，实际返回：

{"code": -32015, "message": "Transaction version (1) is not supported by the requesting client. Please try the request again with the following configuration parameter: \"maxSupportedTransactionVersion\": 1"}

这一次发现阶段的错误是终端记录，不在 E1 成功采集的六个请求中。改用上限 1 后，从包含 System Program transfer 且 meta.err == null 的交易中选得上述样本，再运行已保存脚本完成对账。较晚重跑时，公共 Devnet 可能已裁剪历史或发生重置；脚本报告 unavailable 是环境变化证据，不应据此伪造相同输出。可另选当前仍可查询的公开签名，把新输入与响应保存到新文件，保留本次样本。

实验实际证明的范围： 三种 RPC 查询可以关联同一签名、slot、执行错误和区块位置；本例手续费可用余额差复算；账户读取上下文晚于交易 slot。它没有观察 processed → confirmed → finalized 的变化，没有实测 shred/Geyser 到达顺序，没有制造分叉或重连，没有测量端到端延迟。

后续实验（待验证）​

若要验证实时路径，需要一套版本匹配的节点与 Yellowstone 插件，或提供明确协议及回放条件的服务。订阅同一签名涉及的账户、transaction 与 slot，保留节点版本、Bank 身份、原始消息和本地单调时钟；同时轮询 RPC 状态。shred 接收方还需能验证 Leader 签名、恢复完整数据并解码 Entry，不能把收到任意 UDP 包当作交易出现。

重连实验应覆盖：同 slot 断线、窗口内重放、超出窗口、慢消费者、服务重启与切换来源；比较最终链完整性及重复处理后的业务结果。分叉与失败执行可在匹配版本的本地网络设计可控案例。上述步骤本篇均未执行；在没有同交易、同观察点、同步时钟及足够样本之前，不提供“快多少毫秒”的结论。

8. 工程取舍与一手资料​

业务问题优先观察面仍需补齐
尽早发现可能进入账本的交易负载能验证并恢复数据的 shred / deshred 来源执行结果、分叉与最终确认；来源访问条件另行核查
持续处理账户写入与执行元数据版本匹配的 Geyser / Yellowstone幂等、乱序、过滤完整性、背压和有限回放；按需选择 commitment
查询签名状态、交易详情和当前账户支持所需方法及历史保留的 RPC限流、归档范围、账户快照边界和跨接口对账
精确历史账户状态自有快照 + 完整变更日志或账本重放分叉处理、初始化一致性、存储与重放版本；标准历史交易 RPC 不能代替

核心结论的证据分层如下。源码证明的是指定提交的逻辑，实验只证明当次端点返回的结果；恢复方案属于基于这些边界提出的工程建议。

结论一手证据核验情况 / 范围
Leader 先执行，记录请求接纳入队后 commit，PoH 异步生成 EntryConsumer、记录队列、PoH已读最新稳定发布的固定源码；未运行该版本 validator
广播按组件编码，跟随节点经统一调度器执行Broadcast、Blockstore processor、任务处理器已读固定源码；没有本次 shred 抓包
TowerBFT 与 Alpenglow 的 commitment 更新路径不同commitment service、root 工具已读运行模式分支；没有由版本号推断 E1 网络启用状态
失败指令仍可能有费用和 nonce 状态变化account_saver已读分支；失败交易实验待验证
Yellowstone 提供 commitment 和有限 from_slot 回放协议、服务实现已读配套最新稳定发布源码；未验证插件部署及回放服务配置
历史交易查询与账户状态查询不同RPC 实现、账户实现、E1 输出固定源码与 Devnet 查询分别核验
可复算的转账及费用E1 输出单个 Devnet 样本；无性能推断

组织方式参考 Solana 数据路径：Shred Stream、gRPC 与 RPC，没有沿用其中未经本篇复核的延迟或服务能力数字。官方方法索引：RPC、getTransaction、getAccountInfo、getSignatureStatuses。这些官方网页在本次抓取时均返回 HTTP 429，故这里只作为延伸阅读入口，不声称已完成当日网页内容复核；接口行为的证据是上表固定源码及实验响应。
