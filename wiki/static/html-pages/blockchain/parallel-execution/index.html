Parallel Execution · Source Walkthrough

区块里的交易，
凭什么能同时跑？

并行执行不是「多开几个线程」。它要回答三件事： 哪些交易没有依赖、冲突了怎么收场、 凭什么保证结果和串行一模一样。 不同链的差别，本质上是对这三个问题的不同取舍。

01 · 心智模型

并行是手段，等价顺序状态机才是目标

任何并行执行方案，都要在「不改变状态转换结果」的前提下，把顺序状态机改写成并发程序。 区别只在于三件事的答案：依赖怎么发现、冲突怎么处理、正确性怎么证明。

A

哪些交易能并行

读集和写集不相交的交易可以同时执行；写同一个键的交易必须排队。 依赖是在执行前声明，还是执行后检测，决定了整套架构。

B

冲突了怎么办

加锁等待、回滚重放、或者直接串行执行。乐观方案把冲突推迟到校验阶段， 用「重放」换吞吐；悲观方案在执行前就把冲突交易挡在门外。

C

怎么证明没算错

最终状态必须等于按区块顺序串行执行的结果。提交顺序、版本号、gas 计费都要可复现； 否则并行度越高，错得越快。

并行执行的正确性约束是：最终状态 ≡ 按区块顺序串行执行的结果。所有算法都在为这个等式买单。

范式代表依赖从哪来冲突怎么处理主要代价
静态声明（悲观） Solana、Sui owned object 交易自带账户 / 对象声明 加锁 + 调度；冲突交易等待或失败 声明粒度粗，热点账户天然串行
乐观检测 Block-STM、Sei、Monad 执行时记录读写集与版本 读集校验失败就重放 重放放大、多版本内存
区块级声明 BAL（EIP-7928） 区块执行后生成，随区块传播 不改变首次执行；并行 IO / 校验 区块体积、验证与预取开销
流水线与专用架构 Solana TPU、Monad、MegaETH、Hyperliquid 按层拆分（共识 / 执行 / 存储） 核心状态机顺序执行，外围并行 通用性弱，依赖工程与硬件
先分清「执行并行」和「验证并行」。 并行执行要发现交易之间的依赖；并行验证只需要重放已知结果。 BAL 属于后者——它让「第二遍」可以并行，而第一遍仍然要顺序执行来产生它。

02 · 依赖判定

并行的边界，是读写集的交集

两笔交易冲突，当且仅当一笔写了的键，被另一笔读过或写过。 难点不在判断冲突，而在于：执行之前，你根本不知道会碰哪些键。

冲突的三种形态教学模型
// 三笔交易对同一个键 K 的操作
T1:  write K = 1     // WAW：两个写，谁最后生效？
T2:  read  K         // RAW：读到的是谁写的值？
T3:  read  K; write  // WAR：读完之后又被改

// 并行执行只关心一件事实：
// 「我读到的值，在提交前有没有被更低序号的交易改掉」

实际实现里通常不需要区分 WAW / RAW / WAR，只维护「读到的版本」并在提交前校验。

粒度决定并行度

粒度越粗，冲突越容易被误判；粒度越细，元数据和校验成本越高。 账户级（Solana）天然把同一账户的所有交易串行化； 存储槽级（EVM 系）能把同一合约的不同槽拆开。

交易级账户级对象级存储槽级
粒度典型系统一个并行单元误判冲突的典型场景
账户Solana一笔交易锁定的所有账户同一 AMM 池、同一 mint 的所有交易互斥
对象Sui一笔交易输入的 owned object 集合共享对象（shared object）必须走共识
存储槽EVM 系并行方案、Block-STM一个 (address, slot) 的读或写同一槽被大量交易读写（如 ERC-20 总供应量）
交易纯转账 / 无状态批处理整笔交易任何共享状态都会退化为串行

依赖在什么时候变得可知

1

执行前声明

Solana 的账户列表、Sui 的输入对象都属于这一类。调度器可以在执行前加锁、分组、并行， 代价是声明必须准确且粒度固定。

2

执行后检测

EVM 交易执行前不知道会读哪些槽。Block-STM、Sei 让交易先跑， 记录读写集，再校验版本；冲突就重放。

3

区块级声明

BAL 由区块执行产生并随区块传播。它不帮助第一遍执行， 但让验证、状态根计算、磁盘预取可以并行。

EVM 的根本矛盾：gas 计费依赖状态访问（cold/warm、账户是否存在）， 而访问集只有执行后才知道。于是「先声明再并行」在 EVM 上不成立， 「先乐观执行再校验」或「区块级事后声明」才是可行路径。

03 · 乐观执行

先跑，再验，错了重跑

把「按顺序执行」换成「先并行猜测，再按顺序校验」。 下面这个模拟器用 6 笔交易演示：哪些能一起跑、哪些会被打回、最终如何收敛到串行结果。

第 0 轮
串行基线：A=805 · B=670 · C=770 · D=55 提交顺序始终等于区块顺序；重放次数就是并行付出的代价。
收敛上界 ≤ N 轮 N 笔交易，每轮至少提交一笔

重放一定由「更低序号的交易写了它读过的键」触发。每轮按序校验时， 至少有一笔交易能把读集对上并提交，所以最多 N 轮收敛。

通用算法（教学伪代码）

optimistic.rs伪代码
loop {
    // 1. 并行执行所有未提交交易
    parallel for tx in pending {
        view  = snapshot();
        out   = execute(tx, view);
        reads = view.read_versions(tx.inputs);
    }

    // 2. 按区块顺序校验并提交
    for tx in pending (block order) {
        if reads.version_changed(committed) {
            tx.state = Redo;          // 重放
        } else {
            committed.apply(out[tx]); // 提交
        }
    }

    if pending.is_empty() { break; }
}

提交顺序永远等于区块顺序；并行只改变「谁先算」，不改变「谁先算数」。

三个必须守住的细节

1. 读的是快照，不是最新值。同轮并行执行时，每笔交易看到的是本轮开始时的状态；否则结果依赖调度顺序，不可复现。

2. 校验看版本，不看内容。同一个值被写两次仍然是冲突——否则你无法判断中间是否发生过「写回旧值」。

3. 重放要读最新状态。重放不是把同一笔交易再算一遍，而是拿新的已提交状态重新执行。

代价不对称：一次冲突会让一笔交易重算，还可能连锁触发后续交易重放。 所以「冲突率」比「并行线程数」更能决定实际吞吐——这也是为什么所有方案都在优化热点访问。

04 · BAL · EIP-7928

把访问集写进区块，让「第二遍」并行

Block-level Access Lists 强制区块携带完整的读写位置。它的定位不是让第一遍执行并行， 而是让磁盘预取、交易校验、状态根计算和免执行状态更新并行。

它长什么样

区块头新增 block_access_list_hash；BAL 本体通过 Engine API 的 ExecutionPayloadV4.blockAccessList 传输，不放进区块体。

结构按 address → field → block_access_index → change 组织： AccountChanges = [address, storage_changes, storage_reads, balance_changes, nonce_changes, code_changes]。

block_access_index：0 表示执行前系统合约，1..n 表示第 n 笔交易， n+1 表示执行后系统调用与提款。

状态：Last Call（2026-11）；EIP-7773 的 Glamsterdam 硬分叉元提案已引用它， geth 与 reth 已有实现，其他客户端也有相关 PR。

并行磁盘读

知道全部地址与槽位后，可以在执行前把状态批量预取进缓存，I/O 与 EVM 计算重叠。

并行交易校验

验证节点可以按 BAL 分片并行检查交易，不必等前一笔交易的状态结果。

并行状态根 + 免执行更新

后置值都在 BAL 里，可以并行计算状态根；甚至不执行交易，直接把 post-state 装进数据库。

05 · Aptos · Block-STM

把「必须按序」变成版本号

区块顺序已经固定，于是第 i 笔交易的每一层读值都有唯一版本 (i, incarnation)。 顺序从约束变成了索引：多版本内存、按版本校验、按索引提交。

Block-STM

乐观 · 多版本 Aptos v1.38.6 论文 + 开源

交易先并行执行并记录读到的版本；校验时重读，版本对不上就 abort、标记 estimate、换下一个 incarnation 重放；提交严格按 txn_idx 递增。

并行单元单笔交易；同一笔可执行多次（incarnation）
冲突判定读集校验：重读每个 key，比较版本是否仍是当初读到的
冲突处理abort → 写集标 estimate → incarnation + 1 重放
确定性commit_idx 严格递增，提交顺序恒等于区块顺序
block-executor/src/executor.rsL819 · 节选
fn update_on_validation(
    txn_idx: TxnIndex,
    incarnation: Incarnation,
    valid: bool,
    validation_wave: Wave,
    last_input_output: &TxnLastInputOutput<T, E::Output>,
    versioned_cache: &MVHashMap<T::Key, T::Tag, T::Value, DelayedFieldID>,
    scheduler: &Scheduler,
) -> Result<SchedulerTask, PanicError> {
    // 只有第一个抢到 abort 权的线程会成功
    let aborted = !valid && scheduler.try_abort(txn_idx, incarnation);

    if aborted {
        update_transaction_on_abort::<T, E>(
            txn_idx, last_input_output, versioned_cache,
        );
        scheduler.finish_abort(txn_idx, incarnation)
    } else {
        scheduler.finish_validation(txn_idx, validation_wave);
        if valid {
            scheduler.queueing_commits_arm();
        }
        Ok(SchedulerTask::Retry)
    }
}

校验失败不是错误，只是「这一版作废」；try_abort 用 Executed(inc) → Aborting(inc) 的状态迁移保证同一版本最多 abort 一次。

三个关键设计

版本 =（交易索引，incarnation）。读 i 只取索引小于 i 的最新版本；未命中则读区块前状态。

estimate 是依赖预测。abort 时把本次写集标成 estimate；后续交易一旦读到 estimate 可以立刻 abort，不必算到底。

校验只往回看。不需要全局冲突图，只要确认 i 之前没人改过它读的键。

  • 热点账户会放大重放。论文实测：只有 32 个账户时负载接近串行；8 个账户时并行度不超过 8 线程。
  • 顺序负载仍有开销。论文称完全顺序的负载最多约 30% 额外开销；高冲突负载仍有加速——并行度是冲突率的连续函数。
  • 不是「无冲突才并行」。它不需要预声明写集，用上一次 incarnation 的写集做估计；这与 Solana 的静态声明是两条路。
  • 会回退串行。v1.38.6 有 v1 / v2 两套调度器；模块发布、resource group、VM abort、超 gas 等情况会 halt 并回退顺序执行，incarnation 过高也有兜底。
  • 论文数字不是主网数字。110k TPS（Diem）/ 170k TPS（Aptos）@32 线程来自 benchmark；官方只说「runs in production at Aptos」。

06 · Sei · OCC on Cosmos KV

多版本放在 KV 层，而不是 VM 内

Sei 把 Cosmos 的 CacheMultiStore 包成版本索引存储：EVM 的每次读都被记录，校验时比较「值」。 它不要求交易声明访问集，也不依赖 EIP-2930。

Sei OCC

乐观 · 值校验 sei-chain v6.8.0 Cosmos KV 层

每笔交易拿到独立的 CacheMultiStore 和 (绝对索引, incarnation) 版本；读集落盘，校验时比对最新值；冲突重放，超过 10 轮整块退回同步执行。

并行单元单笔交易（deliverTxTask）
冲突判定读集校验，比较该索引之前的最新「值」是否相等
冲突处理invalidate + 依赖等待 + incarnation 递增重放
确定性校验从第一个未 validated 索引推进；全块结束后一次性写回最新值

func (s *Store) checkReadsetAtIndex(index int) (bool, []int, []string) {
    conflictSet := make(map[int]struct{})
    valid := true
    readSetAny, found := s.txReadSets.Load(index)
    if !found { return true, []int{}, nil }

    for key, valueArr := range readSetAny.(ReadSet) {
        if len(valueArr) != 1 { valid = false; continue }
        value := valueArr[0]
        latestValue := s.GetLatestBeforeIndex(index, []byte(key))
        if latestValue == nil {
            if !bytes.Equal(s.parentStore.Get([]byte(key)), value) {
                valid = false
            }
        } else if latestValue.IsEstimate() {
            // 估计值只记依赖，不直接判失败
            conflictSet[latestValue.Index()] = struct{}{}
        } else if latestValue.IsDeleted() {
            if value != nil { valid = false }
        } else if !bytes.Equal(latestValue.Value(), value) {
            valid = false
        }
    }
    // 循环结束后把 conflictSet 排序成 conflictIndices，
    // 再 return valid, conflictIndices, conflictKeys
}

校验比较的是「值」而不是版本号：对 KV 状态足够，但无法识别「改了又改回」的 ABA。

读到 estimate 就立刻放弃

读路径如果命中一个还没确认的估计值，会写 abort 并通过 panic 中断当前执行： 这是用「提前失败」换「少算无用功」。

与 Block-STM 的差别：Sei 把多版本放在 Cosmos KV 层（VersionIndexedStore）， 所以 EVM 与 Cosmos 模块共用同一套 OCC，而不需要 VM 提供读写集。

maximumIterations = 10：超过就把整块切成同步执行，避免病态冲突下的活锁。

  • 不是所有区块都并行。同一收款人、无 calldata 的纯 EVM 转账批次会走同步快路径（anti-pathological 优化）。
  • access list 只影响 gas。Sei 的调度不读 EIP-2930 access list；源码里也没有 DepAccessList / OptimisticScheduler 这些名字。
  • 文档与实现有偏差。官方文档描述过 Dependency Generator、Bloom filter 预筛，但在 v6.8.0 源码中检索不到对应实现——只能当作文档说法。
  • 两层「乐观」别混。区块级预执行缓存（ProcessProposal 里 5s 超时提前跑）与交易级 OCC 是两件事。

07 · Monad · 乐观 + 流水线

先投机执行，再按原序提交

Monad 的执行层把每笔交易放到独立状态副本上跑，然后等前序交易提交、逐项比对读过的账户与存储槽。 对不上就重跑——官方口径是每笔交易最多执行两次。

Monad 执行客户端

乐观 · 槽级校验 category-labs/monad C++ · 开源

每笔交易在独立 State 上投机执行；提交前 prev_.wait() 等前序结果，can_merge 逐账户/逐槽比对原读值；失败则重试一次。

冲突处理重执行；重执行期间阻塞后续提交

can_merge 逐项比较账户与 storage slot 的原读值；只要有一项被改过就返回 false。

官方口径（docs.monad.xyz）

「Pending results are committed serially in the original order of the transactions, checking each input for correctness at the time of commitment.」

「…all state contention is evaluated on a slot-by-slot basis.」——同一合约的不同槽不冲突，热点集中在同一槽。

「…every transaction will be executed at most twice.」——重放上限靠缓存与记忆化支撑，而不是无限重试。

  • 不要求预声明访问集。官方明确不强制 EIP-2930：access list 不区分读/写，无法预判争用。
  • mempool 不做冲突预判。只校验签名、nonce、gas 上限；冲突在提交阶段才暴露。
  • 流水线是另一半。共识与执行解耦，执行可以占满整个区块时间；MonadDB 用异步 I/O、绕过文件系统、持久化 trie 支撑并行读。
  • 代码是开源的。category-labs/monad 是 C++ 执行客户端，monad-bft 只含共识/网络；不要再说「闭源无法分析」。

08 · Solana · Sealevel

把冲突挡在门外：静态账户锁

Solana 的交易在提交时就声明每个账户是只读还是可写。调度器执行前就能加锁、分组、分派， 不需要重放——代价是冲突交易必须排队，且粒度是账户级。

        transaction.is_writable(index).then_some(key)

    .iter()
    .enumerate()

accounts-db/src/account_locks.rsL56
fn can_lock_accounts<'a>(
    &self,
    keys: impl Iterator<Item = (&'a Pubkey, bool)>,
) -> TransactionResult<()> {
    for (key, writable) in keys {
        if writable {
            if !self.can_write_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        } else if !self.can_read_lock(key) {
            return Err(TransactionError::AccountInUse);
        }
    }
    Ok(())
}

bank 层是最后一道闸：AccountInUse 在 consumer 里被标成 immediately_retryable，重新入队而不是写下失败回执。

  • 粒度是账户，不是字段。同一个 AccountSharedData 里改不同字段也互斥；TransactionAccounts 的借用计数只解决单笔交易内部的别名问题。
  • 线程亲和带来顺序。ThreadAwareAccountLocks 只允许「已经持有该账户锁的线程」继续调度，于是同一账户的交易被钉在同一 worker 上按 FIFO 执行。
  • worker 数量有限。banking stage 默认 4 个、最多 64 个 consume worker；并行度还受每账户成本上限约束。
  • 没有 account_deps。v4.4.1 的 SVM 只做顺序执行一批交易，跨交易冲突由上层调度器与 bank 锁负责；旧文章里的 account_deps 结构已不存在。
  • 流水线是另一半。TPU 的 sigverify → banking stage → PoH 是同进程多线程流水线；「并行」不只发生在执行，也发生在阶段之间。

09 · Sui · 对象版本

用对象版本取代加锁

Sui 的并行单元是对象，不是账户：owned 对象的版本由交易指定，shared 对象由共识定序定版。 调度器按输入对象建依赖，冲突在「版本」这一层判定，没有加锁/解锁动作。

pub fn process_tx(
    &mut self,
    tx_digest: TransactionDigest,
    tx: &TransactionData,
) -> BTreeSet<TransactionDigest> {
    let mut barrier_deps = BTreeSet::new();
    for SharedInputObject { id, mutability, .. }
        in tx.kind().shared_input_objects()
    {
        match mutability {
            SharedObjectMutability::NonExclusiveWrite => {
                self.dep_state.entry(id).or_default().insert(tx_digest);
            }
            SharedObjectMutability::Mutable => {
                // 前面有非独占写 → 本交易是 barrier，先等它们
                if let Some(deps) = self.dep_state.remove(&id) {

                }
            }
            SharedObjectMutability::Immutable => (),
        }
    }
    barrier_deps
}

NonExclusiveWrite 目前不允许用户交易使用（源码会拒绝），只用于结算类交易。

  • 并发上限是半核。CausalAdmission 的并发度 = max(1, num_cpus / 2)，另一半留给共识、网络与 checkpoint。

13 · 失败模式

并行方案在哪里失效

所有并行方案都不是「越快越好」：它们在热点、重放、内存和回退路径上各有代价。 这一节用来判断一条链的宣传语在什么条件下不成立。

热点键

同一个 slot / 同一个账户被大量交易读写时，冲突率趋近 1。 Block-STM 论文的实测是：32 个账户的负载已接近串行，8 个账户时并行度不超过 8 线程。

重放级联

一笔交易 abort 会让读到它写集的后续交易一起重算。 estimate 标记的作用就是让后来者尽早 abort，而不是算完再失败——它优化的是浪费，不是正确性。

多版本内存

MVHashMap / 多版本 KV 要保留同一键的多个版本，块越大、冲突越多，内存越高。 Sei 用「块末一次性写回」换取更简单的提交，但峰值内存仍然存在。

声明粒度

Solana 的锁是账户级：同一账户里改不同字段也互斥。 声明粒度越粗，误判冲突越多；越细，声明与校验成本越高。

回退串行

Sei 超过 10 轮迭代整块转同步；Aptos 在模块发布、resource group、VM abort、超 gas 等情况下 halt 回退； Monad 重执行期间会阻塞后续提交。

测量陷阱

论文的 110k/170k TPS 是 32 线程 benchmark；厂商的峰值 TPS 通常不是主网 p99。 比较并行方案时，至少要对齐：串行基线、硬件核数、负载冲突率。

看并行执行性能，先问三个数：冲突率（多少交易要重放）、并行度上限（线程/核数/并发闸门）、串行基线（同一负载顺序执行多快）。 缺一个，TPS 数字就没有可比性。

14 · 工程取舍

为什么没有统一答案

并行执行是吞吐的必要条件，不是充分条件。每种选择都在「通用性、确定性、延迟、实现成本」之间换筹码。

选择收益代价
静态声明执行前无冲突、无重放，延迟可预测声明粒度粗；热点账户/对象排队
乐观 + 版本校验通用，不需要预声明；冲突率低时接近线性加速重放放大；多版本内存；活锁需要兜底
值校验（Sei）实现贴在 KV 层，EVM 与 Cosmos 模块共用无法区分 ABA；需要整块校验与写回
区块级 BAL并行 IO、并行校验、并行状态根、免执行同步区块体积；验证开销；不帮助首次执行
流水线共识/执行/存储重叠，隐藏阶段延迟工程复杂；回退与重放路径难写
单 sequencer省掉共识往返，延迟极低信任与可用性中心化；争议解决依赖证明
专用状态机撮合与清算可极致优化通用性弱；核心闭源，难以外部验证

并行度不是免费的：你要么在执行前付声明成本，要么在执行后付重放成本，要么在架构上付专用化成本。
