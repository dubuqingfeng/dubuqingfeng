BITCOIN CORE · MASTER 32.99 · 19128E8

15 个 CVE，
没有一个是“印钞漏洞”。

2024–2026 这批 Bitcoin Core 披露的共同点，不是改账本， 而是让节点算不完、记不住、写不下、连不上。 它们分布在 compact block、P2P 背压、mempool 策略、脚本验证、 undo 文件、日志和 addrman 里。

01 · 先把结论放前面

它们不是“比特币被攻破”，而是节点被拖垮

15 个 CVE 里没有增发、没有共识分裂、没有私钥泄露。 影响集中在可用性：远程崩溃、CPU/内存/磁盘耗尽，以及一个会让矿工无法出块的 mempool 不一致。

A

崩溃型

脚本检查的 use-after-free、compact block 的断言、32 位大小计算溢出、undo 文件位置回绕、addrman 溢出。共同点是“触发后节点直接退出”。

B

资源型

用重复 inv、暂停的发送队列、TCP urgent data、慢验证交易、日志和坏区块把 CPU、内存或磁盘吃满。

C

状态机型

compact block 与 reorg 后的 TRUC sibling eviction。状态没有清干净，后续消息就会走进错误分支，甚至让矿工无法出块。

读这批漏洞最值得带走的不是 CVE 编号，而是一条规律： 所有“外部输入 + 内部状态 + 无上限资源”的组合，最终都会变成 DoS。

04 · 攻击面：P2P 下载

Compact block 是一个“先猜后补”的状态机

BIP152 用 6 字节 short ID 表示交易，先发 cmpctblock， 缺交易再用 getblocktxn / blocktxn 补齐。 只要“补齐”这一步的状态没清干净，后面的消息就会踩到旧状态。

1 / 6
Peercmpctblock
→
InitDatamempool / extra
→
getblocktxn缺哪些 tx
→
FillBlock重建 + 清状态
→
IsBlockMutatedmerkle + witness
→
ProcessBlock进入验证

CVE-2024-35202

第二次 blocktxn 触发断言

High

影响：< 25.0 · 修复：25.0 · PR #26898

short ID 碰撞或恶意不匹配会让 FillBlock 失败，节点回退请求完整区块， 但旧的 PartiallyDownloadedBlock 仍然留在请求表里。 第二个 blocktxn 再次调用 FillBlock，命中“只能调用一次”的断言，节点崩溃。

cmpctblock→blocktxn 失败→GETDATA 回退→第二个 blocktxn→assert
当前源码：把“只能一次”变成显式状态 
// blockencodings.cpp · FillBlock
header.SetNull();
txn_available.clear();

IsBlockMutatedFn check_mutated{...};
if (check_mutated(block, /*check_witness_root=*/segwit_active)) {
    return READ_STATUS_FAILED;
}
// net_processing.cpp · ProcessCompactBlockTxns
if (partialBlock.header.IsNull()) {
    RemoveBlockRequest(block_transactions.blockhash, pfrom.GetId());
    Misbehaving(peer, "previous compact block reconstruction attempt failed");
    return;
}

攻击者不需要真的撞 short ID，构造不承诺在 merkle root 里的交易即可强制失败。修复把 assert 换成 READ_STATUS_INVALID，并让重复消息进入惩罚分支。

CVE-2025-62859

witness malleation 卡住区块处理

Medium

影响：< 29.2 / 30.0 · 修复：29.2 / 30.0 · PR #32646

compact block 的 short ID 基于 txid，witness 不在 txid 的承诺里。 恶意 peer 可以在 blocktxn 里篡改 witness；旧逻辑在重建后过早清掉下载状态， 再发现 witness commitment 不匹配时，回退到同一个 peer 的 GETDATA，等 10 分钟。

cmpctblock→blocktxn 篡改 witness→重建后检查失败→GETDATA 同 peer→10 min 等待
当前源码：在返回 OK 前检查 witness root 
// blockencodings.cpp
IsBlockMutatedFn check_mutated{m_check_block_mutated_mock
    ? m_check_block_mutated_mock : IsBlockMutated};
if (check_mutated(/*block=*/block,
                  /*check_witness_root=*/segwit_active)) {
    return READ_STATUS_FAILED; // Possible Short ID collision
}
// net_processing.cpp · 失败后的分流
if (status == READ_STATUS_FAILED) {
    if (first_in_flight) {
        // 回退请求完整区块
        MakeAndPushMessage(pfrom, NetMsgType::GETDATA, invs);
    } else {
        RemoveBlockRequest(hash, pfrom.GetId());
        return;
    }
}

控制 3 个 high-bandwidth peer，或节点运行 -blocksonly 时，可反复触发。修复把 witness mutation 检查提前到 FillBlock 内部，并让下载状态不可复用。

CVE-2024-52922

先 announce，再 withhold

Medium

影响：< 25.1 · 修复：25.1 / 26.0 · PR #27626

旧版每个区块只向一个 peer 请求。攻击者先通过 headers 或 cmpctblock 宣布区块，然后不回应；节点最多等 10 分钟才断开并重试。 攻击者可以多连接重复，拖慢网络收敛和矿工收益。

announce→占据唯一 in-flight 槽→不响应→10 min 超时→重复
当前源码：同一区块最多 3 个并发请求

// net_processing.cpp
typedef std::multimap<uint256,
    std::pair<NodeId, std::list<QueuedBlock>::iterator>>
    BlockDownloadMap;
BlockDownloadMap mapBlocksInFlight;

修复还要求其中一个请求来自 outbound peer，并在删除单个 peer 的请求时重置 stalling 计时器。

CVE-2026-117348

重复 orphan inv 让节点停顿

Medium

影响：29.0–29.5, 30.0–30.4, 31.0–31.2 · 修复：30.5 / 31.3 / 32.1 · PR #35878

一条 inv 最多 50,000 项，旧代码不跳过重复项。 攻击者先发一个有很多缺失父交易的 orphan，然后把同一 wtxid 重复 50,000 次； 每个条目都触发 orphan 父列表构建和 mempool/filter 检查，单条消息可卡住十几秒。

orphan tx→很多缺失 parent→inv 重复 wtxid 50k 次→父检查重复 50k 次→消息循环停顿
当前源码：每条 INV 内部的去重集合 
std::unordered_set<uint256, SaltedUint256Hasher>
    seen_txids{0, m_txhash_hasher};
std::unordered_set<uint256, SaltedUint256Hasher>
    seen_wtxids{0, m_txhash_hasher};

auto& seen_hashes{inv.IsMsgWtx() ? seen_wtxids : seen_txids};
if (!seen_hashes.insert(inv.hash).second) continue;

去重范围是单条 INV 消息，不会影响跨消息的正常重试。MSG_WITNESS_TX 被当作 txid 处理，txid 与 wtxid 分开去重。

05 · 攻击面：网络资源与身份

背压不是“有队列上限”就够了

这三条都发生在 PeerManager 之外的网络层：发送队列、select() 后端、Tor 入站身份。 它们的共同点是“把外部 peer 的属性错误地当成可信输入”。

CVE-2026-117349

暂停的 pre-BIP31 peer 无限增长

Medium

影响：29.0–29.4, 30.0–30.3, 31.0–31.1, 32.0 · 修复：29.5 / 30.4 / 31.2 / 32.1 · PR #36667

发送队列超过 nSendBufferMaxSize 后，节点把 peer 标记为 fPauseSend，但仍然会把交易 INV 排进队列。 支持 BIP31 nonced ping 的 peer 会在 20 分钟无响应后断开； 不支持 BIP31 的 peer 可以永远 paused，让队列无上限增长。

慢读 peer→fPauseSend→仍排队 tx INV→无 BIP31 超时→内存增长
当前源码：记录 pause 起点，超时断开 
// net.cpp · SocketSendData
const bool pause_send{node.m_send_memusage +
    node.m_transport->GetSendMemoryUsage() > nSendBufferMaxSize};
if (pause_send && !node.fPauseSend) {
    node.m_pause_send_since = NodeClock::now();
}
node.fPauseSend = pause_send;

// net.cpp · InactivityCheck
if (node.fPauseSend) {
    const auto last_pause{node.m_pause_send_since.load()};
    if (now > last_pause + TIMEOUT_INTERVAL) return true;
}

公告给出的增长速率约为入站 2MB/h、出站 5MB/h。修复没有改变背压阈值，只是给“暂停”加了最长时间。

官方公告 PR #36667 源码
CVE-2026-117350

TCP urgent data 绕过 select() 背压

Medium

影响：非 Linux 的 29.0–29.4, 30.0–30.3, 31.0–31.1, 32.0 · 修复：29.5 / 30.4 / 31.2 / 32.1 · PR #36665

Linux 使用 poll()，其他平台使用 select()。 旧 select 后端无条件把每个 socket 放进 err fdset； TCP urgent（out-of-band）数据会触发 exceptional condition，处理时读 socket， 绕过 fPauseRecv 的背压，队列可无限增长。

paused peer→TCP urgent data→select 异常事件→仍然 read→队列增长
当前源码：只有请求 RecvEvent 才监听异常 
// util/sock.cpp · select() 分支
if (events.requested & RecvEvent) {
    FD_SET(s, &recv);
    FD_SET(s, &err);
}
if (events.requested & SendEvent) {
    FD_SET(s, &send);
}
if (events.requested & (RecvEvent | SendEvent)) {
    socket_max = std::max(socket_max, s);
}

Linux 不受影响。Windows、macOS、BSD 受影响；公告说恶意 peer 可以较容易地让这些节点 OOM。

CVE-2025-62860

Tor 入站连接被错误白名单

Medium

影响：< 28.3 / 29.2 / 30.0 · 修复：28.3 / 29.2 / 30.0 · PR #33395

入站 Tor 连接看到的 IP 是本地 Tor daemon（通常是 127.0.0.1 或局域网）。 如果 -whitelist 覆盖这个地址，所有 onion 入站都会被当成受信 peer， 解锁更高的 DoS 配额并关闭部分隐私保护。

Tor daemon 本地地址→匹配 -whitelist 网段→onion inbound 获得权限→DoS / 隐私边界被放宽
当前源码：onion inbound 传入空 optional 
// net.cpp
const bool inbound_onion = std::find(
    m_onion_binds.begin(), m_onion_binds.end(), addr_bind)
    != m_onion_binds.end();

AddWhitelistPermissionFlags(
    permission_flags,
    inbound_onion ? std::optional<CNetAddr>{} : addr,
    vWhitelistedRangeIncoming);

只有设置非默认 -whitelist 的节点受影响；但很多把 Bitcoin Core 与 Tor 一起打包的发行版正是这样配置，公告提到曾有数千个主网节点受影响。

06 · 攻击面：内存池与策略

Policy 不是共识，但 policy bug 可以让矿工停摆

TRUC 和脚本验证都属于“节点自己的规则”。它们不会让区块变成无效， 但会让节点拒绝自己刚刚从区块里恢复出来的交易，或者把 CPU 耗在重复验证上。

CVE-2025-62861

reorg 后 TRUC sibling eviction 破坏 mempool

High

影响：28.0–28.2, 29.0–29.1 · 修复：28.3 / 29.2 / 30.0 · PR #33504

BIP431 的 TRUC 规则限制一个未确认祖先/后代。它是 policy，不是共识， 所以合法区块里可以出现“一个 TRUC 父交易带多个子交易”的拓扑。 reorg 把断开的交易用 bypass_limits=true 重新加入 mempool 时， 旧代码仍然执行 sibling eviction，可能踢掉恢复的交易却留下它的子交易。

TRUC 拓扑进入区块→reorg 重新加入→sibling eviction 运行→父被踢、子还在→模板校验失败
当前源码：reorg 路径不再执行 TRUC 检查 
// validation.cpp · MemPoolAccept::PreChecks
if (!args.m_bypass_limits) {
    // Perform the TRUC checks, using the in-mempool parents.
    if (const auto err{SingleTRUCChecks(
            m_pool, ws.m_ptx, ws.m_parents,
            ws.m_conflicts, ws.m_vsize)}) {
        // sibling eviction / TRUC violation
    }
}

受影响的节点在执行过这种 reorg 后，getblocktemplate 会持续失败，直到重启重新加载 mempool。修复把整段 TRUC 逻辑放进 !bypass_limits。

官方公告 PR #33504 源码
CVE-2025-46598

未确认交易的最坏 CPU 验证

Low

影响：< 30.0 · 修复：30.0 · PR #32473 / #33050 / #33105

攻击者发送最终会被拒绝、但不会触发断连的非标准交易。 旧路径在分类失败原因时会用放宽的 flags 再跑一遍脚本， 叠加 legacy ECDSA 每次重新序列化整笔交易，单笔可能耗时数秒；重复发送可延迟区块传播。

非标准 tx→脚本失败→放宽 flags 重跑→sighash 重新序列化→秒级 CPU

07 · 攻击面：脚本与区块验证

两条最“底层”的崩溃：生命周期与地址空间

这两条都不是网络协议问题，而是 C++ 对象生命周期和 32 位整数运算。 它们也最能说明：共识代码里“看起来不会失败”的早退，可能非常昂贵。

CVE-2024-52911

脚本检查的 use-after-free

High

影响：0.14.0 – 28.x · 修复：29.0 · PR #31112

ConnectBlock 把脚本检查分发给后台线程。每个 CScriptCheck 只持有指向 PrecomputedTransactionData 的指针。 旧代码中 CCheckQueueControl 先于 txsdata 构造，且某些失败路径提前 return，没有等待后台线程；C++ 逆序析构让 txsdata 先释放，后台线程读到已释放内存。

带 PoW 的区块→ConnectBlock 早期失败→提前 return→txsdata 析构→后台线程读取→UAF
当前源码：声明顺序 + 统一 Complete 
// validation.cpp · ConnectBlock
// Precomputed transaction data pointers must not be invalidated
// until after `control` has run the script checks.
std::vector<PrecomputedTransactionData> txsdata(block.vtx.size());
std::optional<CCheckQueueControl<CScriptCheck>> control;
if (auto& queue = m_chainman.GetCheckQueue();
    queue.HasThreads() && fScriptChecks) {
    control.emplace(queue);
}

// 失败不再立刻 return，而是写入 state 后 break
if (!state.IsValid()) break;

if (control) {
    auto parallel_result = control->Complete();
    if (parallel_result.has_value() && state.IsValid()) {
        state.Invalid(BLOCK_CONSENSUS,
            strprintf("block-script-verify-flag-failed (%s)",
                      ScriptErrorString(parallel_result->first)),
            parallel_result->second);
    }
}

修复同时把 CCheckQueue 改成能携带具体 ScriptError 的结果， 并把 Wait() 改成 Complete()。 攻击需要有效 PoW 的区块；公告认为 RCE 理论可能但受输入约束，实际不太可能。

CVE-2025-46597

32 位系统的区块大小乘法溢出

Low

影响：32 位 < 29.1 / 30.0 · 修复：29.1 / 30.0 · PR #32530

CheckBlock 用 GetSerializeSize(...) * 4 > MAX_BLOCK_WEIGHT 检查大小。32 位 size_t 下，区块序列化超过 1GB 时乘法溢出， 检查被绕过，写盘时崩溃。理论触发需要受害者把 -maxmempool 设到 3GB 以上， 且已有约 1GB 交易；32 位系统最多 4GiB 内存，因此极难。

32-bit size_t→>1GB 区块→* 4 溢出→跳过 MAX_BLOCK_WEIGHT→写盘崩溃
当前源码：32 位参数上限

    block.vtx.size() * WITNESS_SCALE_FACTOR > MAX_BLOCK_WEIGHT ||
    ::GetSerializeSize(TX_NO_WITNESS(block)) * WITNESS_SCALE_FACTOR
        > MAX_BLOCK_WEIGHT) { ... }

// node/mempool_args.cpp
static constexpr int MAX_32BIT_MEMPOOL_MB{500};
constexpr bool is_32bit{sizeof(void*) == 4};
if (is_32bit && *mb > MAX_32BIT_MEMPOOL_MB) {
    return util::Error{...};
}

// kernel/caches.h
inline constexpr uint64_t MAX_DBCACHE_BYTES{
    sizeof(void*) == 4 ? 1_GiB
                       : std::numeric_limits<uint64_t>::max()};

修复是“间接”的：限制 32 位节点的 mempool 和 dbcache，阻止构造出 1GB 级别的 compact block 重建条件，而不是改掉乘法本身。

08 · 攻击面：存储、日志与地址管理器

“写不下”比“算不完”更安静

undo 文件、日志和 addrman 都不会影响当前区块的共识， 但它们能让节点在几天或几个月后突然退出，或者让运维无法从磁盘告警里看出根因。

CVE-2026-117346

undo 文件位置 32 位回绕

Low

影响：64 位 < 29.5 / 30.4 / 31.2 / 32.1；32 位与 FAT32 仍受影响 · PR #36669

模式一：状态机

失败路径必须把状态恢复到“可再次进入”或“明确终止”。compact block 的 header 清理、TRUC 的 bypass_limits、undo 的位置，都属于这一类。

模式二：资源上限

每个外部输入触发的队列都要有上限和超时：发送队列、日志、undo 文件、addr ID。只加“队列容量”不加“最长时间”仍然会漏。

模式三：平台边界

32 位 size_t、Windows long、FAT32 4GiB、select 与 poll 的语义差异，都会让同一份代码在不同平台上变成不同漏洞。

节点运营 checklist

  • 确认版本至少是 30.5 / 31.3 / 32.1；29.x 已 EOL。
  • 32 位系统即使升级也无法完全消除 117346；计划迁移到 64 位，避免 FAT32。
  • 非 Linux 节点优先升级 117350；Linux 的 poll 路径不受影响。
  • 使用 Tor 且设置 -whitelist 的节点，升级到 28.3 / 29.2 / 30.0+，并检查是否把 onion inbound 错误放行。
  • 监控磁盘、debug.log 增长、getblocktemplate 失败、peer 发送队列和 OOM。
  • 32 位节点的 -maxmempool 现在硬上限 500MB，-dbcache 上限 1GiB。

升级之外的观察点

  • 区块模板失败：如果 reorg 后 getblocktemplate 持续失败，重启可清空 mempool，但根治要升级 28.3/29.2/30.0+。
  • 日志限速：看到 [*] 前缀说明有源位置被抑制；控制台仍输出，但文件日志会缺失，别误判为“没有日志”。
  • paused peer：新版本会在 20 分钟超时断开，旧的“永远 paused”连接会消失。
  • Tor 权限：升级后 onion inbound 不再继承地址白名单，依赖白名单的运营脚本需要重新评估。
不要用“没有增发”来低估这批漏洞。 62861 会让矿工无法出块，117350 可以远程打爆非 Linux 节点，52911 是 UAF； 对基础设施来说，可用性就是安全边界。

12 · 常见误区

别把 DoS 读成“币没了”

“High 就是能偷币”

不是。52911/35202 是崩溃，62861 是出块停机；这批公告没有增发、没有私钥泄露、没有共识分裂。

“所有节点都受影响”

46597 只影响 32 位；117350 只影响非 Linux；62860 需要非默认 -whitelist；117346 的 64 位利用条件极其苛刻。

“升级内核就够了”

32 位和 FAT32 在 117346 修复后仍有文件大小限制；需要迁移到 64 位文件系统和平台。

“日志限速会丢关键证据”

控制台不受影响，只有写文件被抑制；出现 [*] 前缀说明有源位置超限。对排障要同时看控制台。

“TRUC 是共识规则”

它是 policy，合法区块可以违反。reorg 恢复交易时必须绕过 policy，否则就会出现“区块有效、mempool 不一致”。

“compact block 只省带宽”

它还是一个下载状态机。short ID、witness、重复 blocktxn 都能影响区块处理，而不仅是网络流量。

“undo 溢出只影响矿工”

准备阶段是矿工做的，崩溃的是受害节点；Windows/32 位甚至不需要 reorg，只要文件过 2GiB。

“LLM 扫出来的都是低危”

117348/117349/117350 都是 Medium；Project Loupe 的发现经过人工验证，不能按来源打折。

这批漏洞真正教给我们的，是三条工程原则： 失败路径要清状态、每个队列要有上限和超时、每个平台边界都要单独验证。 共识代码不会因为“看起来很安全”而安全。
