PropAMMs · Market Structure & Source Walkthrough

流动性不再躺着，
它开始报价。

PropAMM（Proprietary AMM）不是一条新公式，而是一种新的做市组织方式： 做市商用自有资金，在链上部署一个只属于自己的交易程序； 价格在链下算，承诺在链上验。它把 CEX 的报价频率和 AMM 的原子结算拼在了一起。

01 · 心智模型

先有资产负债表，再有 AMM

传统 AMM 先有一池被动流动性，价格由交易把它推着走；PropAMM 先有一个做市商， 再由做市商持续告诉链上“我现在愿意在什么价格、接多大的单”。曲线只是报价的载体，不是商业模式的起点。

A

公允价

价格发现主要发生在 CEX 和跨市场套利里。PropAMM 的链下引擎把 CEX 中间价、 Pyth、成交与库存信号揉成一个 fair value。

B

报价函数

把 fair value 翻译成 bid / ask：一半是 spread（风险补偿）， 一半是 skew（库存引导），再叠加单笔上限、报价有效期和库存硬边界。

C

自营库存

没有 LP 份额，没有存款人。Vault 里的资产属于做市商自己， 盈亏、库存风险和资金效率都由这一张资产负债表承担。

D

链上护栏

链上程序不负责“发现价格”，它负责“兑现承诺”： 报价有没有过期、单子有没有超限、库存会不会越界、钱够不够付。

PropAMM 的核心不是「用什么曲线」，而是「谁有资格改价格、改完多久有效、改错了谁承担」。

曲线决定报价形状；权限、时效和库存边界决定它能不能在有毒流量里活下来。
形态定价来源流动性来源更新方式谁承担库存风险
恒定乘积 AMM x·y = k，交易驱动 任何人都能加池 每次 swap 自动移动价格 LP 共同承担
集中流动性 CLMM 区间内的 x·y = k LP 提供区间头寸 swap 移动价格，LP 主动调区间 LP 共同承担

名字先别混：DODO 的 PMM ≠ Solana 的 Prop AMM。 DODO 的 PMM 是 “Proactive Market Maker”，指的是一条围绕预言机价格调整的曲线，流动性仍然对 LP 开放； Solana 语境里的 Prop AMM 是 “Proprietary AMM”，指的是一种运营结构：做市商自有资金、自建程序、自己定价。 两者可能都用到“主动做市”的思想，但不是同一个东西。本页讨论后者。
也不是传统意义上的“暗池”。 暗池隐藏的是订单流和交易意图；PropAMM 的交易、账户和资金流都在链上可见。 它隐藏的是定价逻辑和库存策略——这让有毒交易者更难精确地挑价，但也让普通用户更难审计它到底公不公平。

02 · 为什么偏偏是 Solana

因为“撤单”可以便宜到按 CU 卖

PropAMM 需要高频改价。改价本身不产生收益，所以每次改价的成本必须低到可以忽略； 同时改价交易还要能在排序里抢到 taker 前面。Solana 的低费用、高吞吐和按 CU 计价的拍卖机制， 恰好把这两件事同时变得可行。

01

报价更新极便宜

据 Helius 2025-08 的拆解，HumidiFi 的一次预言机更新只需要约 143 CU， 而一笔典型的 Jupiter 聚合 swap 大约要 150,000 CU。前者不到后者的千分之一。

更新越便宜，做市商越敢把 spread 压窄；spread 越窄，聚合器越愿意路由；路由越多， 库存周转越快。这是一个正反馈。

02

CU 就是新的排队货币

Jito 一类拍卖按 tip per CU 排序，而不是只看绝对 tip。 一笔 143 CU 的更新，只要很小的 tip 就能排到很前面；这相当于给做市商一个便宜的“撤单优先权”。

它不能消除逆向选择，但能把“价格已经动了、报价还没更新”的窗口压到更短。

03

聚合器是现成的分销

Jupiter 在 Solana 聚合器里占绝对主导。新 PropAMM 只要接一次聚合器， 就能拿到原本分散在钱包、前端和机器人里的零售订单流。

代价是：聚合器成了事实上的“券商”，谁被接入、谁被排在前面，会直接影响做市商的生存。

04

零售流量 + 可组合结算

Solana 的零售交易占比高，订单流相对“干净”；同时交易可以在一笔原子交易里完成， 做市商不需要承担跨链或链下结算的对手方风险。

这让 PropAMM 可以专注在流动性的“最后一公里”，而不是自己去做一条链或一个撮合引擎。

≈150k CU 一笔典型聚合器 swap（同一来源）
>60% PropAMM 在 SOL/USDC 成交量中的占比（2025 年数据，峰值约 86%）
这些数字是市场快照，不是永久常数。 份额、费用和更新成本都随竞争快速变化；把它们当成“结构性优势的量级”，不要当成今天的精确行情。 页面里的代码与机制分析，比任何单一时点的 TVL / volume 排名更耐久。
为什么“便宜改价”会改变做市行为机制推导
传统订单簿：
  改一次价 ≈ 撤单 + 下单 + 签名 + 付 gas
  → 改价有固定成本
  → 只能围绕一个较宽的价差做

PropAMM：
  改一次价 ≈ 写 4 个参数（mid / spread / skew / size）
  → 改价近乎免费
  → 可以把价差压到“只覆盖真实风险”
  → 但一旦更新没落地，旧报价会立刻变成别人的套利机会

低成本不是免费午餐：它把竞争从“谁能挂单”变成了“谁能在正确的时间改对参数”。

所以它天然是“专业选手”的游戏

你需要同时具备：低延迟价格源、库存与对冲模型、Solana 程序优化能力、聚合器接入能力， 以及 24/7 的风控值班。缺一项，报价就会在某个时刻变成别人的提款机。

这也是为什么主流 PropAMM 大多由成熟做市团队运营，而不是由一个开放的 LP 社区投票决定参数。

03 · 报价生命周期

一笔 swap 背后，至少有三只看不见的钟

PropAMM 的难点不在“算出一个价格”，而在“让这个价格在正确的时间、以正确的数量、被正确的人拿到”。 把生命周期拆开，会看到链下、排序层和链上各自在管一段。

t−2 · 链下
价格发现 CEX 中间价、Pyth 推送、跨所基差、近期成交与波动率进入模型，形成 fair value 与风险预算。
t−1 · 链下
报价决策 在 fair value 上叠加 half-spread、库存 skew、单笔上限和方向性限制；决定这一轮要不要更新。
t0 · Solana
报价上链 一笔轻量交易写入 mid、spread、skew、max size 和 quote slot。链上只信任自己读到的 slot，不信任客户端传的时间。
t1 · 聚合器
路由比价 聚合器读取各 venue 的报价（或链下缓存的报价），把订单拆到最便宜的一条或几条路径上。
t2 · 交易者
CPI 调用 交易者的 swap 通过 CPI 进入 Vault。此时链上会重新检查报价是否还有效，而不是相信聚合器看到的旧价格。
t3 · Vault
护栏与结算 检查 halt、freshness、max size、库存边界、token account 归属；通过后先收 input，再付 output，最后发事件。
t4 · 链下
库存回写与对冲 引擎读事件 / 余额，更新库存与 skew；必要时在 CEX 或别的 venue 对冲，再进入下一轮报价。
CEX

毫秒级

真实价格发现的速度。PropAMM 的 fair value 在这里被推着走，做市商无法控制它，只能跟。

Slot

约 400ms

Solana 的出块节奏。报价的有效期通常用 slot 表示；它是链上唯一可信的时间来源。

TTL

几个 slot

报价的存活时间。太短会被聚合器判为不可用，太长会在行情跳动时被逆向选择。

最危险的窗口：CEX 已经动了，链上还没动。 假设报价在 slot N 写的是 150.00，slot N+1 外部价格跳到 151.00（+67 bps）， 而更新交易在 slot N+2 才落地。此时任何能在 N+1 成交的 taker，都可以按 150.00 买走， 做市商瞬间承担约 67 bps 的 markout 损失。报价越便宜、更新越慢，这个窗口越值钱。

PropAMM 的竞争，本质上是「把报价的有效窗口压到比别人的套利反应更短」。

低成本更新、CU 拍卖、私有 mempool、预言机推送延迟，都是围绕这个窗口做文章。

04 · 报价数学

四个参数，撑起一张双边报价

一个最小可用的 PropAMM 不需要复杂的曲线：给定 mid、half-spread 和 skew， 就能推出 bid / ask；再给定库存和单笔上限，就能决定“接不接、接多少”。 下面用开源实现 PropAMM Forge 的代码走一遍。

// 价格都用定点整数，链上没有浮点数
factor(side) = (10000 + skew_bps) × (10000 ∓ spread_bps) / 10000²
bid = floor(mid_e9 × factor(bid)) // 做市商买 base，向下取整
ask = ceil (mid_e9 × factor(ask)) // 做市商卖 base，向上取整
out(base→quote) = floor(amount_in × bid_e9 / 1e9)
out(quote→base) = floor(amount_in × 1e9 / ask_e9)

一个具体例子

mid = 150.00 USDC/SOL，half-spread = 10 bps，skew = −20 bps。

先移动 mid：150.00 × (1 − 0.002) = 149.70。

再向两边展开：bid = 149.70 × (1 − 0.001) = 149.5503；ask = 149.70 × (1 + 0.001) = 149.8497。

报价宽度约 0.2994 USDC，等于 20 bps；但整张报价被 skew 向下压了 20 bps。

pub fn side_price_e9(
    params: &QuoteParams,
    side: Side,
) -> Result<u128, QuoteError> {
    if params.mid_e9 == 0 {
        return Err(QuoteError::QuoteNotSet);
    }
    let factor = side_factor(params, side)?;
    match side {
        Side::BaseToQuote =>
            mul_div_floor(params.mid_e9, factor, FACTOR_DENOM),
        Side::QuoteToBase =>
            mul_div_ceil(params.mid_e9, factor, FACTOR_DENOM),
    }
}

bid 向下、ask 向上：两边都朝做市商有利的方向取整。这个不对称是故意的。

side_factor · 同一个因子同时管 skew 和 spreadL325
fn side_factor(params: &QuoteParams, side: Side)
    -> Result<u128, QuoteError>
{
    let denom = i32::from(BPS_DENOM);

    let skewed = denom
        .checked_add(i32::from(params.skew_bps))
        .ok_or(QuoteError::Overflow)?;
    if skewed <= 0 {
        return Err(QuoteError::InvalidParams);
    }

    let spread = i32::from(params.spread_bps);
    if spread >= denom {
        return Err(QuoteError::InvalidParams);
    }
    let sided = match side {
        Side::BaseToQuote => denom.checked_sub(spread),
        Side::QuoteToBase => denom.checked_add(spread),
    }.ok_or(QuoteError::Overflow)?;

    let skewed = u128::try_from(skewed)
        .map_err(|_| QuoteError::Overflow)?;
    let sided = u128::try_from(sided)
        .map_err(|_| QuoteError::Overflow)?;
    skewed.checked_mul(sided).ok_or(QuoteError::Overflow)
}

skew 移动整张报价，spread 把两边推开。两者相乘，而不是相加；这样 skew 不会改变报价宽度。

为什么要用乘法？

如果 skew 和 spread 相加，skew 越大，实际点差会被“吃掉”或“撑大”。 乘法把两个语义分开：skew 管中心，spread 管宽度。

这也让参数有清晰的边界：spread 必须小于 10000 bps，skew 不能把 mid 乘成非正数。 链上程序在写入报价时会把两边都算一遍，任何一边越界都直接拒绝。

库存 skew：让报价替你“劝退”不想要的库存

inventory_skew_bpsL194 · 节选/改写
pub fn inventory_skew_bps(
    inventory: &Inventory,
    mid_e9: u128,
) -> Result<i32, QuoteError> {
    let base_value = u128::from(inventory.base_amount)
        .checked_mul(mid_e9)?;
    let quote_value = u128::from(inventory.quote_amount)
        .checked_mul(PRICE_SCALE)?;
    let total = base_value.checked_add(quote_value)?;
    if total == 0 { return Ok(0); }

    // (base 价值 − quote 价值) / 总价值，单位 bps
    let skew = (i128::try_from(base_value)? -
                i128::try_from(quote_value)?)
        .checked_mul(10000)?
        .checked_div(i128::try_from(total)?)?;
    i32::try_from(skew).map_err(|_| QuoteError::Overflow)
}

正值 = base 太多；负值 = quote 太多。两条腿都用 mid 估值，避免同一库存因报价方向不同而算出不同 skew。

引擎怎么把 skew 变成报价

PropAMM Forge 的内置模型先算库存 skew，再按“离硬边界还有多远”线性放大 spread 和 shift：

load = |skew| / max_skew_bps，spread 从基准值扩到最大值， shift 从 0 扩到最大偏移；如果 base 太多，就把整张报价往下压，让 vault 变成“买 base 更便宜”的地方。

这解释了一个反直觉的设计：库存越偏，报价越宽，但同时越偏向于吸引能修正库存的流量。 如果只看“越偏越宽”，会以为它在劝退所有交易；实际上它是在用价格挑交易。

库存边界只约束“换”，不约束“状态”。 行情跳动本身就能让库存 skew 越界；如果规则写成“swap 后必须在边界内”， 一个已经越界的 vault 会连“把库存换回来”的交易都拒绝，反而把自己锁死。 所以代码只在“这笔交易让它更远”时才拒绝：after > bound && after > before。

先校验价格与有效期，再算输出，再查数量与库存。顺序不是随意的：越便宜的检查越早做。

三个容易写错的细节

1. 单笔上限用 base 腿。否则同一个 max_size_base 在两个方向上代表不同的经济规模。

2. 零输出必须拒绝。否则用户可以“付一点 input，拿走 0”，或者反过来被协议白嫖。

3. 报价和成交必须共用同一份数学。PropAMM Forge 把 compute_swap 同时编译进链上程序、路由器适配器和测试；否则链下算出的 quote 与链上执行会在某个舍入边界上分叉。

05 · 链上程序

Vault 不存余额，只存“现在的报价”

一个 PropAMM 的链上状态可以很小：权限、交易对、报价参数、有效期和库存边界。 真正的库存放在 token account 里，链上每次 swap 现读现算。这样少一次状态同步，就少一处可能对不上的账。

三个角色，三把钥匙

owner：资金所有者。可以改报价签名者、提款、停机，但不参与日常报价。

pricing_authority：热钱包，只负责写报价。被攻破时，攻击者不能直接转走资金，只能报错价或撤掉报价——而错误报价仍受库存边界和单笔上限约束。

halt_authority：可以单独停机，但拿不到资金。适合放在更安全的冷环境或监控服务里。

update_quote：时间必须来自链上

为什么 clear_quote 是单独指令

Anchor 的编码器会把缺失字段写成 0。如果 mid_e9 = 0 同时表示“清空报价”， 一个漏传参数的构建脚本就会静默地把价格撤掉，而不是报错。

所以 update_quote 明确拒绝 0，清空则走一条没有参数可忘的独立指令。 这是很小的 API 设计，但它决定了故障时是“响亮地失败”还是“安静地出错”。

停机的 vault 不允许再报价；但允许清空报价——移除价格永远是安全动作。

swap：先收钱，再付钱，库存从余额读

输出金额直接来自 compute_swap 的结果，不再读一次余额。少两次 reload，也避免“读到的余额”和“算出的余额”不一致。

几个不显眼但关键的工程点

Account 约束：base_treasury.key() == vault.base_vault、mint 必须匹配。否则攻击者可以塞入自己的 token account 把 vault 掏空。

Box 两个 Mint：Anchor 的 try_accounts 把十个账户的反序列化状态放在 4 KiB 栈帧里；四个 TokenAccount 加两个 Mint 会到 4104 字节，超过 4 KiB。Box 不是风格问题，是能不能编译过的问题。

没有 partial fill：要么整单成交，要么报错。这让路由器的模拟结果与链上执行更容易一致。

没有 msg! 成功日志：成功路径不打日志，格式化字符串在 CU 预算里很贵；事件足够做链下索引。

这套程序的“信任边界”很清晰： 链下负责“价格可能是多少”，链上负责“这笔交易在数学和会计上是否成立”。 它不试图在链上重新发现价格，也不假装自己能防住所有有毒流量；它只是把做市商的承诺变成一个可组合、可审计的接口。

06 · 生产环境逆向

HumidiFi：链上不是定价器，是“承诺验证器”

大多数头部 PropAMM 不开源、不发 IDL。研究者只能下载链上程序、反编译、猜指令。 HumidiFi 是目前被拆得最细的一个样本：它展示了生产级 PropAMM 如何把“价格”做成一份链下承诺， 再让链上程序只做验证和记账。

先划边界：下面内容来自第三方对 2026-03 下载的 humidifi.so 的反编译与标注， 不是官方源码，也不保证与今天链上字节一致。它适合用来理解可能的设计空间，不适合当作审计结论。

它为什么不走 Anchor

Anchor 会暴露 8 字节 discriminator、公开 IDL 和标准错误码，接入成本低，但也会把指令布局暴露给所有人。 HumidiFi 用了自定义分发：从指令数据最后一个字节读出 selector，再和长度做异或：

disc = (last_byte ^ ((len-1) >> 3) ^ 0x3a) & 0xff，大于 0x17 就 clamp 到 0x18。

这不是密码学安全，只是把“猜指令”从读 IDL 变成读二进制。它提高了集成门槛，也降低了被自动化工具有针对性地挑价的速度。

docs/archaeology.md · 指令分发第三方逆向
// entrypoint 里的 selector 计算
uVar11 = (last_byte ^ ((len - 1) >> 3) ^ 0x3a) & 0xff;
if (0x17 < uVar11) uVar11 = 0x18;   // clamp to 24

// 大部分指令的 payload 还会原地 XOR 解密
key = 0xc3ebbae2ff2fff3a;
counter = 0;
for each 8-byte chunk i:
    chunk[i] ^= counter ^ key;
    counter += 0x0001000100010001;

// 例外：0x00、0x06、0x0d、0x0e 不解密
// 其中 0x00 用最后 32 字节校验 program id，防跨程序重放

XOR 不是加密，只是混淆；真正的安全来自权限检查、PDA 校验和价格承诺的哈希绑定。

价格承诺：一份 512 字节的“成交意图”

同一个 payload 换一个 pool、换一个程序、换一个状态，哈希就对不上。这让“重放昨天的好价格”变得困难。

三层价格结构

1. 预言机基准价：链下引擎签名提交，链上只验证它是不是最新的、是否绑定当前状态。

2. 价格阶梯：18 个 u64 定义 3 档 bid / 3 档 ask 的边界和权重；交易规模落在哪一档，就用哪一档的价格。这些字段在 state 里也按字段 XOR-masked，直接读账户并不能还原参数。

3. 成交价：在选中的档位内插值，再做手续费和方向调整。最终成交价写回 state，并以 XOR 混淆后发事件。

这意味着链上并没有跑一条 x·y = k；它跑的是一棵“价格 → 档位 → 插值”的查表机。 曲线可以很复杂，但链上只需要验证结果落在承诺范围内。

143

CU 的更新

预言机更新被压到约 143 CU，更新交易成本约 9,998 lamports。低价更新是高频报价的前提。

512B

的承诺

主交易指令携带 512 字节的签名负载；链上验证 program id、PDA、哈希和账户归属后，再执行两笔 token CPI。

0x0c

的 kill switch

反编译里能看到 “disabled ixn” 的运行时开关，而这个二进制里的 0x0c 被标成永久关闭。它说明程序保留了“按版本关掉某条指令”的能力，是风控也是中心化。

这个样本真正说明的是“分工”： 价格发现留在链下，链上只保留可验证的承诺、库存状态和转账。 这样既能把更新成本压到极低，又能让聚合器和用户在没有 IDL 的情况下完成原子结算。 代价是策略不透明、升级权集中、外部只能通过行为反推。

07 · 曲线的变体

还是 x·y = k，只是把坐标平移了

不是所有 PropAMM 都用“报价表”。Obric 这类 “proactive AMM” 仍然用一条曲线， 但它把曲线围绕目标库存和预言机价格做平移、缩放。参数很少，效果却很像“链上版做市商报价”。

// 以 Obric 的 Sui 结构为线索；下面是教育性复刻中的等价形式（非官方源码）
v₀ = targetX × concentration
K = v₀² × multX / multY
base = v₀ + reserveX − targetX
out(x→y) = K / base − K / (base + amountIn)

三个参数分别在做什么

targetX：做市商希望的 base 库存目标。reserve 偏离 target 时，曲线自动把价格推向“把库存拉回来”的方向。

concentration：虚拟深度倍数。v₀ = targetX × concentration；concentration 越大，曲线在目标价附近的深度越深、滑点越小。

multX / multY：预言机乘数。当 reserve = target 时，边际价格正好是 multX / multY；改这两个数，就相当于把整条曲线搬到新的公允价。

PropAMM.sol · Obric 风格的报价教育性复刻 · L436
function _quoteXtoY(
    bytes32 pairId,
    uint256 amountXIn,
    PairParameters memory params
) internal view returns (uint256 amountOut) {
    TradingPair storage pair = pairs[pairId];

    uint256 v0 = pair.targetX * params.concentration;
    uint256 K = (v0 * v0 * params.multX) / params.multY;

    uint256 base = v0 + pair.reserveX - pair.targetX;

    amountOut = K / base - K / (base + amountXIn);
}

当 reserveX = targetX 时，base = v₀，边际价格 K/base² = multX/multY。这就是“围绕预言机价做市”的数学表达。

“Proactive” 不等于 “没有曲线”。 这类设计的精髓是：曲线本身不变，变的是曲线的锚（mult）和深度（concentration）。 做市商不需要每笔都报价，只需要持续把锚搬到最新公允价附近；链上成交仍然由一条确定性的公式完成。 这比“每笔都签名报价”更便宜，但也更依赖参数更新的时效。

08 · 集成与 ABI

没有标准 IDL，每个 PropAMM 都是一门方言

传统 DEX 有相对稳定的 AMM 接口；PropAMM 为了隐藏策略、优化 CU，往往连指令格式都自定义。 结果是：聚合器每接一家，就要写一套账户顺序、选择器和参数编码。pmm-sim 把这种“方言”摊开在了代码里。

pmm-sim/src/cfg.rs · HumidiFi 指令编码L157 · 节选
fn humidifi_instruction_data(
    selector: &[u8], amount_in: u64, direction: u8
) -> Vec<u8> {
    let swap_id: u64 = 1500;
    let mut data = Vec::with_capacity(25);
    data.extend_from_slice(&swap_id.to_le_bytes());
    data.extend_from_slice(&amount_in.to_le_bytes());
    data.push(direction);
    data.extend_from_slice(&[0u8; 7]);   // padding
    data.extend_from_slice(selector);

    // 和 HumidiFi 二进制一致的 XOR 混淆
    let key = u64::from_le_bytes(
        [58, 255, 47, 255, 226, 186, 235, 195]
    );
    for (i, chunk) in data.chunks_exact_mut(8).enumerate() {
        let qword = u64::from_le_bytes(chunk.try_into().unwrap());
        let pos_mask = 0x0001_0001_0001_0001u64
            .wrapping_mul(i as u64);
        let obfuscated = qword ^ key ^ pos_mask;
        chunk.copy_from_slice(&obfuscated.to_le_bytes());
    }
    data
}

连“选择器放最后”这种细节都要单独实现；这不是标准 ABI 能覆盖的。

“同一个价格，不同调用者”是真实存在的。 pmm-sim 提供 --spoof=jupiter|okx|dflow|titan：把 CPI 调用者的身份伪装成某个聚合器。 一些 PropAMM 会给白名单聚合器更优的费率或更大的额度；这不是漏洞，而是订单流分层。 它同时意味着：报价不是全局统一的，取决于“谁在问”。普通用户看到的聚合器报价，和做市商给某个路由的报价，可能不是同一张表。

pmm-sim 做了什么

它把 HumidiFi、SolFi V2、Obric V2、ZeroFi、Tessera、GoonFi、BisonFi 的真实程序与账户快照放进 LiteSVM， 在本地复现 swap、拆分路由、benchmark CU / 汇率，并支持伪装 CPI 来源。

这对研究者很有用：不用连主网就能比较“同一 slot、同一金额”下各家的报价和计算成本。 但它仍然是模拟，不等于主网真实成交，也不覆盖聚合器的完整路由逻辑。

“集成税”的后果

对聚合器：每接一家都要写适配器、做审计、维护账户顺序；谁能被接入，本身就是一种稀缺资源。

对做市商：没有标准接口意味着更高的护城河，但也更难被多路由发现；只接一家聚合器时，流量会高度集中。

对研究者：没有 IDL 就只能靠反编译和链上行为；可验证性下降，但也不是完全黑箱——资金流、事件和账户变化仍然公开。

10 · 风险与边界

它优化了价格，也集中了风险

PropAMM 让零售用户拿到更窄的价差，但它把“谁承担库存风险、谁有权改价格、谁决定谁能接入” 这些问题从 LP 社区转移到了少数做市商和聚合器身上。理解收益，也要理解这些结构性代价。

01逆向选择 / 有毒流量

机制：外部价格先动，链上报价还没更新；能更快成交的人按旧价买走。

缓解：低成本高频更新、CU 拍卖、私有订单流、报价有效期、按规模分层定价。

残留：只要更新不是原子跟随 CEX，窗口就存在；越窄的价差越依赖更新速度。

02报价密钥与重放

机制：报价签名者被攻破，攻击者可以报出偏离公允价的价格；或者重放旧签名。

缓解：热钱包只拿报价权、程序 id 绑定、pool state 哈希绑定、slot 有效期、库存硬边界。

残留：密钥泄露后，攻击者仍能在边界内持续“慢速抽血”；监控与停机权很关键。

03库存与对冲风险

机制：单边行情让库存迅速偏向一侧；链上边界能阻止继续恶化，但不能阻止已经发生的亏损。

缓解：skew、spread 扩张、单笔上限、CEX 对冲、跨 venue 调仓。

残留：对冲本身有基差、资金费率和执行风险；极端行情下流动性可能同时消失。

04闭源与升级权

机制：没有 IDL、没有源码，策略和升级内容都不可审计；程序升级可以随时改变规则。

缓解：链上资金流与事件可观测、第三方反编译、聚合器审计、社区监控。

残留：“可观测”不等于“可验证”；用户无法独立证明报价函数没有被临时改动。

05聚合器依赖与准入

机制：PropAMM 的流量高度依赖少数聚合器；接入、排序和报价缓存都由聚合器决定。

缓解：多聚合器接入、直接前端、API / RFQ、做市商自有流量。

残留：新 venue 很难冷启动；聚合器成为事实上的准入者，可能强化中心化。

06报价分层与“看人下菜”

机制：部分 venue 对白名单聚合器给更优价格或更大额度；同一笔 swap 换个调用者，价格可能不同。

缓解：透明披露、聚合器比价、独立模拟（如 pmm-sim）。

残留：普通用户很难知道自己拿到的是不是“最优那张表”；路由层的权力进一步集中。

07资本与长尾资产

机制：做市商用自己的钱承担库存风险，因此只愿意做流动性好、可对冲的主流资产。

缓解：多资产库存、跨链 / CEX 对冲、动态额度。

残留：长尾资产仍然依赖公共 AMM；PropAMM 越成功，流动性越向头部资产集中。

08没有 LP 收益，也没有 LP 保护

机制：没有 LP 份额，用户不能“存款吃手续费”；做市商的盈亏完全内部化。

缓解：对交易者而言，更窄的价差就是收益；对做市商而言，专业风控是唯一护城河。

残留：一旦做市商退出或停机，池子可能瞬间没有流动性；没有 LP 可以“接盘”。

  • 它的报价有效期是几个 slot？更新失败时会不会自动失效？
  • 单笔上限、库存边界、停机权分别由谁控制？
  • 它是否对不同聚合器 / 调用者给不同报价？

代码与信任

  • 程序是否可升级？升级权限在谁手里？有没有时间锁？
  • 报价函数是否与链上执行共用同一份数学？舍入方向是否偏向 vault？
  • 价格承诺是否绑定 pool state / program id / slot，能否重放？

11 · 对比与指标

不要只看 TVL，看“有效价差”和“报价存活率”

PropAMM 的资本效率很高，TVL 往往不能反映真实可交易深度；同样，成交量也可能被聚合器拆分和刷量放大。 评估它，应该看更接近交易体验的指标。

Effective spread 成交价相对 mid 的实际偏离，比“挂单价差”更接近用户成本。
Markout 1s / 10s 成交后 1 秒 / 10 秒的价格变化。做市商是否被系统性逆向选择，看这个最直接。
Quote uptime 报价在多少比例的时间里是新鲜且可成交的。停机、过期、额度耗尽都会拉低它。
Update CU 一次报价更新的计算成本。它决定了做市商能承受多高的更新频率。
Quote age p50 / p95 成交时报价已经存活了多少 slot。越高，越依赖“更新能抢在 taker 前面”。
Volume / TVL 资金周转率。PropAMM 通常远高于公共池，但这不代表风险更低。
TVL 陷阱：PropAMM 的自营库存可以很少，却通过高频周转做出很大的成交量。 看到“TVL 只有几百万、日成交量几亿”不一定是数据错误；但它也意味着，一旦做市商撤资或停机， 深度会比 TVL 看起来更脆弱。

PropAMM 把 AMM 从“流动性池”变成了“流动性接口”。

接口背后是一个做市商、一张资产负债表和一套风控；曲线只是它对外说话的方式。
