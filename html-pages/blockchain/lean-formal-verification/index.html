Lean 4 · Proof Assistant · Ethereum / Solana

测试只能说明你试过；

形式化验证不是“再跑一遍测试”，而是把规格、程序模型和证明写成机器可检查的对象。 这篇从 Lean 4 的“命题即类型”讲到链上实践：以太坊的 EVM/字节码验证，和 Solana 的账户模型与 sBPF。

01 · Why Formal Verification

测试、审计、定理，不是同一件事

测试覆盖你想到的输入；审计依赖人的经验；定理要求“对所有输入、在给定模型下”成立。 代价和边界也完全不同。

方法能回答什么不能回答什么成本
单元/集成测试这些输入下行为正确没测到的输入、组合爆炸低
模糊测试在一段时间/随机分布下没崩不构成“对所有输入成立”中
人工审计已知模式、设计缺陷、经验判断不穷尽状态空间，不可机器复核中高
形式化验证在 spec + model 下，定理对所有输入成立spec 错了、模型不忠实、TCB 被攻破高
!

形式化验证不是“没有 bug”的同义词。 它证明的是：在你看待世界的方式（模型）和你说想要的东西（规格）之下，程序满足规格。 规格写错，证明越漂亮越危险。

02 · Lean in One Page

命题即类型，证明即项

Lean 4 是依赖类型论的证明助手：类型可以依赖值，命题是类型，证明是让该类型非空的项。 证明写完后由一个小内核检查，而不是“相信 tactic”。

依赖类型

类型可以带参数和值，例如 Vector α n 把长度放进类型；很多“数组越界”在类型层就消失。

命题即类型

P : Prop 是一个类型；证明 h : P 是一个项。证明 P → Q 就是构造一个函数。

可信内核

simp/omega 只是构造证明项的助手；最终由 Lean kernel 检查。TCB 比“整个 tactic 库”小得多。

1
初始目标

证明 transfer 保持总余额。

2
展开定义

simp [transfer] 把函数展开成算术目标。

3
算术收尾

omega 使用前提 amt ≤ s.a 关闭目标。

-- 目标状态示意；真实项目由 lake build 检查 ⊢ (transfer s amt).a + (transfer s amt).b = s.a + s.b
Transfer.lean · 结构示意（未在本地执行）Lean 4
import Mathlib

structure State where
  a : Nat
  b : Nat

def transfer (s : State) (amt : Nat) : State :=
  { s with a := s.a - amt, b := s.b + amt }

theorem transfer_preserves_total
    (s : State) (amt : Nat) (h : amt ≤ s.a) :
    (transfer s amt).a + (transfer s amt).b = s.a + s.b := by
  simp [transfer]
  omega
⊢

常见 tactic： simp 化简、omega 线性算术、induction 归纳、cases 分类讨论、 rw 重写、exact 给出证明项。它们是“写证明”的工具，不是可信公理。

03 · The Verification Stack

一条证明链，和一条信任链

形式化验证从来不是“代码 → 定理”一步。中间有规格、模型、细化关系、证明检查器， 以及编译器/硬件等仍然被信任的东西。

1. 规格 Spec

余额守恒、权限、状态机不变量、gas 上界。写错就证明错的东西。

人写 / 需审阅
2. 模型 Model

EVM / sBPF / 程序语义。模型不忠实，定理对真实链上行为没有意义。

可信 / 需 conformance
3. 细化 Refinement

“这段字节码/程序”满足“这个规格”。可能是 Hoare triple，也可能是编译器正确性定理。

被证明
4. 证明检查

Lean kernel 检查证明项；#print axioms 可以列出依赖的公理。

小内核
5. 编译/运行

Solc、LLVM、SBF 工具链、密码库、硬件。证明通常不覆盖这些，除非另有验证编译器。

仍需信任

浅嵌入 vs 深嵌入

浅嵌入：在 Lean 里直接写程序逻辑/状态机，证明容易，但和真实字节码之间有 gap。 深嵌入：把 EVM/sBPF 指令、内存、gas 都建模，能证明字节码，但模型和证明成本更高。

源码级 vs 字节码级

源码级证明依赖编译器正确；字节码级证明绕开编译器，但必须信任 EVM/sBPF 语义。 Verity 选择“证明编译器到 Yul，信任 solc 到字节码”；Blanc 选择直接对部署字节码证明。

!

“Proof of the wrong theorem”是最常见的失败。 证明通过只说明“Lean 接受了这个命题”；你还要问：这个命题是不是我真正想要的？ 模型是不是链上真正跑的？字节码/源码是不是同一个版本？

04 · Practice on EVM / SVM

从语义到字节码：两条链的实践

以太坊的 Lean 生态分成 EVM/Yul 语义、共享原语、字节码验证栈和经过证明的编译器；Solana 则围绕账户模型、sBPF 与编译后的 .so。 选哪一层，决定了你还要信任什么。

LeanEVM

EVM 语义

Philogy 的 Lean 4 EVM 可执行模型（Cancun），用 Ethereum BlockchainTests 做 conformance。

  • 目标：给“编译到 EVM 的编译器”一个可引用的语义
  • 256 位字用 8×32-bit limb，证明与 BitVec 256 等价
  • WIP；不是完整的主网客户端

Jaune / Blanc

字节码

Jaune 是可执行 EVM 规范；Blanc 在其上做智能合约验证栈，直接针对部署字节码。

  • Blanc 宣称覆盖 Curve 3pool/3Crv、USDC、Vyper nonreentrancy、EIP-7002
  • 强调 exact gas、liveness、无额外公理（README 声称）
  • 字节码从主网读取，不信任产生它的编译器

EVMYulLean

EVM + Yul

Nethermind 的 EVM/Yul 形式模型；Yul 的 primops 尽量直接复用 EVM 语义。

  • 适合 Yul 级推理与编译器前端验证
  • 有 conformance 与 Yul 语义测试
  • 模型本身仍是信任边界

EthLib

共享原语

Ethereum 官方的 Lean 原语库：U256、执行、共识、网络等分层定义与证明。

  • 让不同 Lean 项目共享同一套定义
  • 部分原语可通过绑定给客户端用
  • 仍在演进，不是完整执行层规范

Verity

编译器

Lean 4 写的智能合约 DSL/编译器，编译器各层有正确性证明；也可导入 Solidity。

  • DSL → CompilationModel → IR → Yul 分层证明
  • Yul → 字节码交给 pinned solc，属于信任边界
  • README 声称编译器证明栈 0 公理、无 sorry

EquiVM

细化

针对 EVM 字节码的 refinement 证明，基于 Stele 与 EVMLean 语义。

  • 把“字节码行为”与“规格”用 refinement relation 连接
  • 示例包含 ERC20 正确性
  • TCB 包含 EVM 语义与 Lean 内核
项目证明对象绕开了什么仍然信任什么
LeanEVMEVM 指令/调用/创建语义无（它是语义基础）模型忠实性、Lean 内核
Jaune / Blanc部署字节码的性质Solidity/Yul 编译器EVM 语义、规格、gas 模型
EVMYulLeanEVM + Yul 语义无（语义基础）模型、conformance
VerityDSL→Yul 编译器正确性手写 Yul 的证明solc 的 Yul→字节码
EquiVM字节码 vs 规格的 refinement源码级证明的编译器 gapEVM 语义、spec、内核
i

实践顺序： 先决定你要证明“部署字节码”还是“编译器输出”。字节码级（Blanc/EquiVM）绕开编译器但模型更重； 编译器级（Verity）证明链更清晰，但 Yul→字节码仍要信任 solc。

Solanalib

原语 / sBPF

Solana Foundation 的实验性 Lean 4 库：账户、指令、PDA、金融形状，以及 sBPF 指令语义。

  • sBPF 语义是 OOPSLA 2025 Isabelle/HOL 形式化的 Lean 移植
  • 用参考 VM 做验证；目标是“Solana 的 Mathlib”
  • README 明确标注 purely experimental

qedsvm

编译后 .so

直接执行/验证编译后的 Solana sBPF 程序，而不是 Rust 源码；生成 Lean Hoare triple。

  • 对选定路径生成带 CU 上界的定理
  • Lean SVM 模型与 Mollusk/Agave 做差分测试
  • 不自动证明任意整个程序；需要 IDL/overlay/trace

Aeneas 提取

Rust 源码

Verified-Privacy-Cash 用 Charon + Aeneas 把 Rust 程序提取成 Lean 模型，再写规格与证明。

  • 示例：transact 指令 12/12 函数透明、71/71 原语 opaque
  • check_public_amount 的两个分支已证明
  • 提取模型 ≠ 已证明整个程序；仍有 shim/未证明部分

Sour / Kani

协议数学

Sour 的 Lean 4 + Kani 证明：池子守恒、LP 上限、OI 上限、正 PnL 守恒等。

  • Lean 证明对 Nat 无界；Kani 对有界输入
  • 账户认证、PDA、CPI 等运行时检查不在纯数学证明范围
  • 适合“资金不变量”而不是“整程序正确”
项目证明对象起点仍然信任什么
Solanalib账户/指令/金融原语、sBPF 语义Lean 定义实验性模型、参考 VM
qedsvm选定字节码路径的 Hoare triple + CU链上 .soSVM 模型、IDL/overlay、路径选择
AeneasRust 函数提取后的模型与规格Rust 源码Charon/Aeneas、shim、未证明部分
Sour / Kani协议资金不变量数学/处理器运行时/账户检查不在范围
!

Solana 的难点在账户，不只是算术。 一个“余额守恒”定理可能完全正确，但如果没有覆盖 owner 检查、PDA 派生、signer 权限、CPI 目标、 account aliasing 和序列化，它仍然不能说明程序安全。qedsvm 的 IDL/overlay 和 Aeneas 的 shim， 正是在补这些“模型与现实之间”的缝。

05 · Choose the Tool

Lean 不是唯一答案

Lean 适合“对所有输入成立”的定理和细化证明；有界模型检查、规则审计、模糊测试各有位置。 生产里通常是组合，而不是二选一。

工具方法覆盖成本适合
Lean 4交互式定理证明无界输入、细化、编译器正确性高核心协议、字节码、编译器
Kani有界模型检查Rust 函数、固定边界中快速 invariant、CI 门禁
Certora规则/符号执行EVM/Solana 合约中规则审计、持续集成
K Framework可执行语义语言/字节码中高语义定义、符号执行
Fuzzing / 审计经验覆盖未知模式、实现细节低中发现“你没想到的输入”
✓

组合方式： Kani/模糊测试快速扫不变量 → Lean 证明关键定理 → 字节码级验证/TEE 信任边界 → 独立审计。 Lean 证明不是“上线许可证”，它只是把某一部分的确定性提高了一个量级。

06 · Trust Boundaries

证明通过之后，还要问什么

看到 lake build 通过，不等于可以上线。下面这些洞，任何一个都能让定理和真实系统脱节。

sorry / admit

证明没写完，但 Lean 仍然接受文件；CI 必须禁止，或用 #print axioms 检查。

axiom

每加一个公理，TCB 就变大。Lean 自带 propext、Classical.choice、Quot.sound；额外的要逐条解释。

native_decide

把“具体计算”交给编译后的求值器；对字节码表、具体常量很方便，但会把求值器/编译器加入信任面。

unsafe / FFI

逻辑层的证明不约束运行时的 unsafe 或外部函数；如果生产路径走 FFI，证明可能不适用。

规格写错

“余额守恒”可能没覆盖手续费、舍入、权限或暂停；定理只对你写的命题负责。

模型不忠实

EVM/sBPF 语义漏掉 gas、异常、调用深度、账户别名；conformance 测试是必要但不充分。

版本错位

证明针对 commit A，部署的是 commit B；字节码 hash、编译器版本、参数都要钉住。

可升级/管理员

代理、admin、治理可以改变行为；证明要覆盖升级路径，或明确“升级后定理失效”。

检查证明的“含金量”Lean
-- 1. 证明里是否还有 sorry？
-- 2. 依赖了哪些公理？
#print axioms transfer_preserves_total

-- 3. 是否有 unsafe / implemented_by / FFI？
-- 4. 定理的 statement 是否真的对应部署字节码？
-- 5. 模型/编译器/参数版本是否钉住？
!

一句话： 形式化验证把“所有输入”这件事变成了可检查的定理，但它也把“规格、模型、信任边界”放到了聚光灯下。 你需要的不只是证明，还需要能解释“这个定理到底说了什么”的人。

最小检查清单

  • 规格：定理是否真的表达业务想要的性质？是否覆盖权限、费用、舍入、暂停、升级？
  • 模型：EVM/sBPF/程序语义是否与链上执行一致？有 conformance/差分测试吗？
  • 细化：定理是对源码、IR、Yul 还是部署字节码？中间信任了哪个编译器/汇编器？
  • 公理：#print axioms 是否只有 Lean 三条？有没有额外 axiom/sorry？
  • 运行时：native_decide、FFI、unsafe、@[implemented_by] 是否进入生产路径？
  • 版本：commit、toolchain、solc/SBF 工具链、链上字节码 hash 是否全部钉住？
  • CI：lake build 是否在干净环境可复现？证明产物/报告是否随代码归档？
  • 人：是否有独立审阅规格与信任边界的人？证明不是审计的替代品。
