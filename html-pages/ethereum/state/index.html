状态不是一张表，
而是一棵可验证的树。

账户、余额、nonce、存储槽都只是内存里的对象；真正进入区块头的， 是从这些对象重新算出来的 stateRoot。 StateDB 负责“改”，MPT 负责“证明”，TrieDB 负责“存”， PathDB/HashDB 决定“怎么存”。

01 · 心智模型

同一份状态，三种身份

读代码时最容易混乱的地方，是把“账户对象”“trie 节点”“数据库键”当成同一个东西。 它们其实是同一份状态的三种表示，生命周期完全不同。

A

内存对象

stateObject 持有 data types.StateAccount、storage 缓存和 code。 修改先落在这里，EVM 看到的是它。

B

可验证树

账户 trie 的 keccak(addr) 分支，存储 trie 的 keccak(slot) 分支。 根哈希进入区块头，任何字段变化都会级联到根。

C

持久化键值

HashDB 用 nodeHash → RLP(node)；PathDB 用 (owner, path) → node，另有扁平账户和槽位。

共识只认 stateRoot。数据库里的扁平状态、缓存、快照，都是为了更快地得到或验证这个根，不是新的共识来源。

层核心问题关键类型是否直接决定共识
StateDB执行期间账户怎么改、怎么回滚StateDB / stateObject / journal否，产出的根才决定
MPT账户和存储如何压缩、哈希、证明trie.Trie / trie.StateTrie是，根哈希
TrieDB节点和扁平状态交给哪个后端triedb.Database / StateSet否，存储实现
PathDB按路径覆盖写，保留最近状态层pathdb.Database / diffLayer / diskLayer否，但影响可回滚范围
HashDB按内容寻址，引用计数回收hashdb.Database / cachedNode否，影响归档能力

02 · 账户

一个账户只有四个共识字段

以太坊没有“EOA 表”和“合约表”两张表。EOA 和合约账户都是 StateAccount，区别只在 CodeHash 是否为空，以及 EVM 会不会执行它的代码。

Account

0x0000…00a1

合约账户

Nonce：账户自己的计数器

EOA 每发一笔交易加一；合约每创建一个合约加一。它不是交易里的 nonce 字段，但交易 nonce 必须与账户 nonce 对齐。

key = keccak256(address)
value = RLP(nonce, balance, storageRoot, codeHash)

core/types/state_account.goStateAccount
type StateAccount struct {
    Nonce    uint64
    Balance  *uint256.Int
    Root     common.Hash // merkle root of the storage trie
    CodeHash []byte
}

字段顺序就是 RLP 顺序。地址本身不在账户体里，地址是 trie 的 key。 EmptyRootHash 表示空存储，EmptyCodeHash 表示没有代码。

EOACodeHash = keccak256(nil)
合约CodeHash ≠ keccak256(nil)
空账户nonce = 0 ∧ balance = 0 ∧ codeHash = empty

原生余额 ≠ 代币余额

StateAccount.Balance 是 ETH，单位 wei。ERC-20 的 balanceOf 是合约存储里的一个槽，读它要执行合约代码。

Code 不在账户体里

账户只存 codeHash；字节码按哈希存在 CodeDB。这样同一份代码可以被多个账户引用，也避免 trie 节点过大。

Nonce 也会改根

Nonce 是账户 RLP 的第一项。即使余额和存储都不变，仅 nonce 变化也会让账户 trie 的叶子变化，最终改变 stateRoot。

“合约账户”不是一种独立的数据结构。 当一笔交易 CALL 到某个地址时，EVM 读取该账户的 CodeHash；如果有代码，就加载并执行。 DELEGATECALL 执行的是目标代码，但读写的是调用方账户的存储。

03 · 余额、nonce 与存储槽

写一笔状态，要穿过四层缓存

stateObject 不是简单地“改一个 map”。它把当前交易、当前区块、已提交值分开， 这样 EVM 的 revert、SSTORE 的 gas 规则和区块末尾的统一提交才能同时成立。

dirtyStorage 当前交易写

EVM 刚写入的值。revert 时随 journal 回滚。

pendingStorage 交易结束待提交

Finalise 把 dirty 挪进来，等待区块末写入 storage trie。

originStorage 区块内已读原值

第一次 SLOAD 的缓存；也是 SSTORE gas 和回滚判断的基准。

uncommittedStorage 自上次 commit 的脏槽

记录该槽的原始值，区块末统一生成 storage diff。

if prev == value {
    return prev
}

写入前必须拿到 prev 和 origin：前者用于 revert， 后者用于判断“是否真的偏离了原值”。写回原值会撤销 dirty 标记。

存储槽的键和值

EVM 看到的是 32 字节 key、32 字节 value。进入 MPT 前： key 变成 keccak256(key)，value 去掉前导零后做 RLP。值为零等同于删除该槽。

trie key = keccak256(slot)
trie value = RLP(trimLeftZeroes(value))

Solidity 的 mapping 在哪

对于声明在 slot 0 的 mapping(address => uint256) balances，

slot = keccak256(abi.encode(holder, uint256(0)))

所以 balanceOf(holder) 读的是合约存储 trie 的一个普通叶子，和 ETH 余额完全无关。

SSTORE 不是“直接写 trie”。 它先写 dirtyStorage 并记 journal； 交易结束由 Finalise 汇总到 pendingStorage； 区块结束 IntermediateRoot 才把 pending 写进 storage trie，重算 storageRoot。

04 · MPT

Merkle Patricia Trie：把 64 位十六进制 key 压成一条路径

账户 trie 和每个合约的存储 trie 都是 MPT。MPT 的每个节点要么是 16 路分支， 要么是压缩后的短节点；节点 RLP 编码后取 keccak256，父节点存子节点哈希。

1address0x0000…00a1
→
2keccak25632 bytes
→
3nibbles64 × [0..f]
→
4pathbranch / short

Branch（fullNode）

17 个槽：前 16 个对应下一个 nibble，第 17 个存放“路径在这里结束”的值。 账户和存储的 key 都是定长，所以第 17 槽通常为空。

Short（shortNode）

压缩一段没有分叉的路径。带 terminator 时是叶子，不带时是扩展节点。 编码时使用 compact encoding。

Embedded（< 32 bytes）

RLP 小于 32 字节的节点不单独存哈希，直接嵌入父节点。只有大节点才在数据库里按哈希寻址。

trie/secure_trie.go · 账户与存储StateTrie
func (t *StateTrie) GetAccount(address common.Address) (*types.StateAccount, error) {
    res, err := t.trie.Get(crypto.Keccak256(address.Bytes()))
    // ...
    ret := new(types.StateAccount)
    err = rlp.DecodeBytes(res, ret)
}

func (t *StateTrie) UpdateStorage(_ common.Address, key, value []byte) error {
    hk := crypto.Keccak256(key)
    v, _ := rlp.EncodeToBytes(value)
    return t.trie.Update(hk, v)
}

StateTrie 是“带 key 哈希的 Trie”。账户 key 和存储 key 都会先做 keccak256。

为什么账户 trie 和存储 trie 是两棵树

账户叶子里的 Root 是存储 trie 根。账户 trie 只负责“地址 → 账户元数据”， 存储 trie 负责“槽 → 值”。合约可以有大量存储，不必把槽塞进账户叶子。

accountTrie[keccak(addr)] = RLP(account)
storageTrie[keccak(slot)] = RLP(value)

更新一个槽：storage trie 根变 → 账户叶子的 Root 变 → 账户 trie 根变 → 区块头 stateRoot 变。

编码用途注意
KEYBYTES对外 API 的原始 key账户是 20 字节地址，槽是 32 字节
HEX内存中的 nibble 路径末尾 0x10 表示 value 终止
COMPACT落盘节点的路径编码首字节包含 terminator / odd 标志
RLP节点序列化节点哈希 = keccak256(RLP(node))

05 · StateDB

执行期的写缓存 + 可回滚日志

StateDB 不是“数据库”，而是某一状态根上的执行视图。它缓存账户对象， 用 journal 支持调用帧回滚，最后把变更打包成 StateUpdate。

StateDB 里真正重要的字段

  • stateObjects：活跃账户对象，按地址缓存。
  • stateObjectsDestruct：本区块内销毁过的账户，阻止回读旧存储。
  • mutations：本区块内账户级变更摘要，区块末据此提交。
  • journal：每次改动的逆操作，支持 Snapshot / Revert。
  • reader：绑定 stateRoot 的读取器，扁平状态优先、trie 兜底。
  • dbErr：第一个数据库错误，最终由 Commit 返回。

  1. EVM 执行 SSTORE，调用 StateDB.SetState。
  2. stateObject 比较当前值和原值，写入 dirtyStorage，并由 journal 记录逆操作。
  3. 交易结束，Finalise 把 dirtyStorage 汇总到 pendingStorage，并维护 uncommittedStorage。
  4. 区块结束，IntermediateRoot 并发更新各账户的 storage trie，重算 storageRoot。
  5. 账户 trie 写入新的 StateAccount，得到新的 stateRoot。
  6. commit 收集 AccountUpdate、storage diff、code 和 trie node，生成 StateUpdate。
  7. MPTDatabase.Commit 写 CodeDB、更新 snapshot，再调用 triedb.Update。
  8. PathDB 新增 diff layer；HashDB 把节点放入 dirties，等待引用计数和 Commit/Cap。

06 · TrieDB

把“树”与“怎么存树”解耦

trie 只关心节点、路径和哈希；TrieDB 决定节点写到哪里、保留多少层、是否维护扁平状态和历史。 这就是 PathDB 与 HashDB 能共享同一套 MPT 代码的原因。

triedb/database.go · Database门面
type Database struct {
    disk      ethdb.Database
    config    *Config
    preimages *preimageStore
    backend   backend // hashdb 或 pathdb
}

func (db *Database) Update(
    root, parent common.Hash,
    block uint64,
    nodes *trienode.MergedNodeSet,
    states *StateSet,
) error {
    switch b := db.backend.(type) {
    case *hashdb.Database:
        return b.Update(root, parent, block, nodes)
    case *pathdb.Database:
        return b.Update(root, parent, block, nodes, states.internal())
    }
}

同一次状态提交同时带 nodes（trie 节点）和 states（扁平账户/槽位）。HashDB 只用前者。

两个 Reader 接口

NodeReader.Node(owner, path, hash) 给 trie 用： 按“哪个 trie、哪条路径、期望哈希”取节点。

StateReader.Account(hash) / Storage(acctHash, slotHash) 给扁平日志用： 直接按地址哈希和槽哈希取值，不经过 trie 路径。

NodeReader → pathdb.reader / hashdb.reader
StateReader → pathdb.reader（hashdb 未实现）

HashDB 模式没有扁平状态，StateDB 的读取最终回落到 MPT；可选 snapshot tree 才会提供 flat 快路径。

节点集和状态集不是一回事。 MergedNodeSet 是“树节点怎么变”，用于重建/验证 trie； StateSet 是“账户和槽位现在是什么”，用于扁平读取、快照和状态历史。 PathDB 两者都存，HashDB 只存节点。

07 · PathDB

在内存里叠 128 层 diff，再把最底层压进磁盘

PathDB 用 (owner, path) 定位节点，而不是节点哈希。每个有状态变化的区块新增一个 diff layer， 当层数超过 128 时，最底层被 flatten 到 disk layer。

nodesWithOrigins := newNodeSetWithOrigin(newMergedNodeSet(nodes), origins)

每次提交只挂一层，并不立即写盘；超过 128 层才触发底部持久化。

triedb/pathdb/reader.go · StateReader读取
func (db *Database) StateReader(root common.Hash) (database.StateReader, error) {
    layer := db.tree.get(root)
    if layer == nil {
        return nil, fmt.Errorf("%w: %#x", database.ErrStateUnavailable, root)
    }
    return &reader{db: db, state: root, layer: layer}, nil
}

读取从目标 root 对应的层开始，逐层向父层找；找不到才落到 disk。

数据PathDB 键值
账户树节点"A" + hexPathRLP(node)
存储树节点"O" + acctHash + hexPathRLP(node)

代码"c" + codeHashcontract bytecode

为什么能省空间

按路径覆盖写，同一个节点路径只保留最新版本；不需要像 HashDB 那样为每个历史版本保留节点，直到引用计数归零。

为什么还需要 trie

扁平状态可能不完整（快照还在生成），也可能被错误修改。MPT 是最终校验器：扁平读失败或未覆盖时回落到 trie。

历史与回滚

底部 diff 持久化时写入 state history（反向 diff）。深 reorg 时按 history 反向恢复；可配置保留长度，默认只保留最近一段。

    return blob, nil
}
// Account is unknown to this layer, resolve from parent
return dl.parent.account(hash, depth+1)

账户、槽位、节点都遵循同一套“本层命中 → 父层递归 → diskLayer”的查找。

08 · HashDB

内容寻址、引用计数、显式 GC

HashDB 把每个 trie 节点按 keccak256(RLP(node)) 存。相同子树天然去重； 代价是必须追踪父子引用，并在合适的时机 Commit / Cap 把节点刷盘。

triedb/hashdb/database.go · 结构cachedNode
type Database struct {
    diskdb  ethdb.Database
    cleans  *fastcache.Cache
    dirties map[common.Hash]*cachedNode
    oldest  common.Hash
    newest  common.Hash
}

type cachedNode struct {
    node      []byte
    parents   uint32
    external  map[common.Hash]struct{}
    flushPrev common.Hash
    flushNext common.Hash
}

dirties 是“当前仍被引用的脏节点”；flush-list 按插入顺序串联，用于 Cap 时从旧到新刷盘。

一次区块提交发生什么

  1. Update 按 owner 顺序插入节点；先存储 trie，后账户 trie。
  2. 账户叶子里的 storageRoot 通过 Reference 挂在账户节点上。
  3. 区块头 stateRoot 通过 Reference(root, zero) 增加一个外部引用。
  4. 旧区块 root 通过 Dereference 减少引用；无引用节点级联删除。
  5. 内存超限或达到保留窗口时，Cap / Commit 把节点写入磁盘。
core/blockchain.go · 非 archive 路径GC
bc.triedb.Reference(root, common.Hash{})
bc.triegc.Push(root, -int64(block.NumberU64()))

// 超过保留窗口后，选一个旧 root 落盘并释放引用
if nodes > limit {
    bc.triedb.Cap(limit - ethdb.IdealBatchSize)
}
if chosen := current - state.TriesInMemory; chosen > 0 {
    bc.triedb.Commit(...)
}

Full 节点只保留最近约 128 个状态根对应的节点；更旧的节点被 GC。Archive 节点则对每个 root 都 Commit。

HashDB 的取舍

优点：节点按内容寻址，天然去重；任意历史状态只要节点还在就能读；实现简单，便于归档。

代价：没有扁平账户/槽位，读账户要遍历 trie；需要引用计数和显式 GC；随机写多，状态增长快。

边界：HashDB 的 StateReader 返回“not implemented”，所以 flat 快路径只能来自独立的 snapshot tree。

PathDB

  • 键：(owner, path)
  • 128 层 diff + disk buffer
  • 节点 + 扁平状态一起提交
  • 历史 state 反向 diff
  • path-based（新节点常用）

HashDB

  • 键：nodeHash
  • dirties + 引用计数 GC
  • 只存节点，不存 flat state
  • Archive 保留全部历史节点
  • legacy scheme

09 · 一次交易

把余额、nonce、存储槽串成一条提交链

切换场景，看看同一笔“转账”在状态层到底改了哪些字段。注意：日志和收据不属于状态， 但它们会影响收据根和 bloom。

EOA A → EOA B，转账 1 ETH

只有账户元数据变化，没有合约存储变化。stateRoot 仍然会因为 nonce 和 balance 改变。

对象字段 / 槽位变化落到哪里

交易执行

EVM 读写 StateDB；失败的调用帧由 journal 回滚，但手续费和 nonce 保留。

Finalise

每笔交易结束：空账户清理、自毁处理、dirty → pending；journal 清空。

IntermediateRoot

区块组装时统一更新 storage tries 和 account trie，得到 header.Root。

Commit

生成 StateUpdate，写 CodeDB，更新 snapshot，交给 TrieDB。

TrieDB

PathDB 挂 diff layer；HashDB 进 dirties，等待 Cap/Commit 与 GC。

区块头里的 stateRoot 是“执行完所有交易后的根”，不是每笔交易的根。 Byzantium 之后，收据里不再保存每笔交易的中间状态根； Finalise 在交易边界执行，IntermediateRoot 在区块组装/提交时执行。

10 · 串联

读一条链，写一条链

把前面的模块接起来后，读和写其实是两条方向相反的调用链。 读路径从 StateDB 往下穿透；写路径从 EVM 往上收敛成 StateUpdate，再交给 TrieDB。

READ

读：账户/槽位从哪里来

  1. StateDB.GetBalance(addr)
  2. getStateObject(addr) → 活跃对象或 Reader
  3. Reader.Account(addr)
  4. multiStateReader：flat 优先
  5. flatReader → PathDB flat / snapshot
  6. 未命中 → mptTrieReader → StateTrie.GetAccount
  7. trie.Trie.Get → 逐 nibble resolve
  8. NodeReader.Node(owner, path, hash)
  9. PathDB diff/disk 或 HashDB 节点缓存

trie 是兜底和最终校验；flat state 只是加速层，可能未覆盖或过期。

WRITE

写：一次 SSTORE 如何落库

  1. EVM SSTORE → StateDB.SetState
  2. stateObject.SetState → journal + dirtyStorage
  3. 交易结束 Finalise → pendingStorage
  4. 区块结束 IntermediateRoot
  5. updateTrie → StateTrie.UpdateStorage
  6. Trie.Commit → storage root + NodeSet
  7. UpdateAccount → account trie + stateRoot
  8. StateDB.commit → StateUpdate
  9. MPTDatabase.Commit → CodeDB + snapshot + triedb.Update
  10. PathDB diff layer / HashDB dirties

最终只有 header.Root 进入共识；其余都是本地存储与加速结构。

调用点被调用者为什么需要这一层
StateDBReader把“账户对象缓存”和“持久状态读取”解耦，支持 flat 优先、trie 兜底。
StateDB.commitDatabase.Commit(StateUpdate)把执行结果变成可持久化的状态集与节点集，避免 StateDB 直接依赖后端。
MPTDatabase.Committriedb.Update统一 hash/path 两种 scheme 的入口，同时携带 nodes 与 states。
triedb.Databasepathdb / hashdb不同落盘策略：分层覆盖写 vs 内容寻址 + 引用计数。
trie.TrieNodeReadertrie 不需要知道节点在内存 diff、buffer 还是磁盘，只管按路径取。

一句话串起来：EVM 改 StateDB → StateDB 改 stateObject → IntermediateRoot 改两棵 trie → StateUpdate 收集 diff → TrieDB 选择后端 → 区块头只拿走 root。

11 · 常见误区

读源码时最容易踩的坑

“stateRoot 包含代码”

不包含代码字节，只包含 codeHash。代码按哈希存在 CodeDB；哈希进账户，所以代码仍被根间接承诺。

“nonce 是交易字段”

账户 nonce 是状态字段；交易 nonce 是签名消息的一部分。交易 nonce 必须等于账户 nonce，执行后账户 nonce 加一。

“存储 key 直接进 trie”

EVM 的 32 字节 slot 会先 keccak256 再进 MPT。Solidity mapping 又会在合约层先算一次哈希，所以最终 key 是哈希的哈希。

“写入 0 会保留一个零值”

值为 0 等价于删除槽。MPT 中不存在的叶子和值为 0 的叶子在状态上不可区分。

“flat state 可以单独信任”

扁平状态是加速/快照结构，可能未生成完或被损坏。PathDB 的 Reader 仍把 MPT 作为兜底；multiStateReader 最后才是 trie。

“PathDB 等于 archive”

PathDB 默认只保留 128 层 diff 和有限 state history；archive 需要额外配置和完整历史。能否读旧状态取决于 history 保留范围。

“HashDB 的节点可以随便删”

节点按引用计数存活。少一次 Reference 或多一次 Dereference 都可能导致节点被提前回收，读到 MissingNode。

“Commit 会立刻写磁盘”

StateDB.Commit 不等于落盘：PathDB 的区块写入走 Update 挂 diff layer；HashDB 的 Commit 才递归写节点。PathDB 还要等 cap 把底层 diff 压进 diskLayer，再由 buffer 异步 flush。

12 · 变更雷达

这份最新代码相比旧版，值得注意的变化

基线是 2026-11-20 的 master。以下不是历史回顾，而是读当前代码时会直接影响理解的结构性变化。

01

StateUpdate 成为一等公民

StateDB 不再直接把 trie 节点塞给数据库，而是产出 StateUpdate：账户、存储、代码、节点、原始值一起描述一次状态迁移。提交与存储彻底解耦。

02

Reader 抽象 + 扁平优先

core/state/reader.go 新增 StateReader / ContractCodeReader，multiStateReader 按优先级尝试 flat 和 MPT；还有 64 桶的并发读缓存与命中统计。

03

PathDB 的 buffer / bloom / 异步写

底部 diff 合并进 buffer，使用 bloom 过滤和分层索引降低查找成本；历史先写、buffer 冻结、后台刷盘。读路径对 stale layer 有回退。

04

PBT（EIP-8297）实验路径

core/state/database_pbt.go 与 trie/pbt 引入分区二叉 Trie：一棵树同时持有账户、存储和代码，OpenStorageTrie 返回自身。它是独立命名空间，不是默认 MPT 路径。

05

Amsterdam / EIP-8246 / EIP-7928

Finalise 分叉出 finaliseAmsterdam：非零余额的自毁账户按 EIP-8246 清空 nonce/code/storage 并保留余额，零余额仍删除；同时把 balance/nonce/code/storage 变更汇总进区块级访问列表。

06

并发提交与 CodeDB 拆分

账户 trie 与多个 storage trie 并发 commit；代码从 StateDB 的提交路径中拆到 CodeDB，按 codeHash 批量写并维护全局缓存。

注意版本边界：master 处于 unstable，PBT、Amsterdam 相关逻辑和数据库格式都可能继续变化。 做生产分析时，先固定 commit，再把“共识状态格式”和“本地存储实现”分开看。
