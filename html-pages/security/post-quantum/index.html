01 · Threat Model

Shor 破公钥，Grover 削对称

先把两种量子算法分开：它们影响的不是同一类密码学，迁移优先级也不同。

RSA

量子计算机可在多项式时间内做大整数分解，从公钥恢复私钥。

不再安全
ECC / ECDH / ECDSA

椭圆曲线离散对数被 Shor 攻破；TLS 的 ECDHE、签名的 ECDSA 都受影响。

不再安全
有限域 DH

经典 Diffie-Hellman 同样依赖离散对数；大素数群也挡不住 Shor。

不再安全
对称加密 / 哈希

Shor 对它们没有直接的多项式时间算法；它们主要面对 Grover。

仍可用，需加长
AES-128

Grover 把穷举从 2¹²⁸ 降到约 2⁶⁴；安全级别减半。

迁到 AES-256
AES-256

Grover 后仍有约 2¹²⁸ 的工作量；在可预见的量子模型下仍可接受。

继续使用
SHA-256 原像

原像搜索从 2²⁵⁶ 降到约 2¹²⁸；碰撞安全需要单独评估参数与协议。

关注协议参数
哈希签名

SLH-DSA 依赖哈希安全；Grover 只降低安全余量，不会像 Shor 那样直接破私钥。

保守可选
!

真正紧迫的是 HNDL（Harvest Now, Decrypt Later）： 攻击者今天录下 TLS 流量，等量子计算机成熟后再解密。只要数据的保密期长于“CRQC 到来时间”， 现在就应该把密钥交换迁到 hybrid。签名可以稍后，但证书链和根信任要提前规划。

02 · Families

后量子不是一种算法，是几组不同的数学

NIST 已经标准化 ML-KEM（FIPS 203）、ML-DSA（FIPS 204）、SLH-DSA（FIPS 205）； 但“后量子”不等于“都安全”，SIKE、Rainbow 都已经被攻破。

格密码

主流

Module-LWE / Module-SIS。密钥和密文尺寸相对平衡，适合通用场景。

  • ML-KEM：密钥封装
  • ML-DSA：数字签名
  • Falcon：短签名，实现更难

哈希签名

保守

只依赖哈希函数的安全性；状态管理简单（无状态），但签名很大。

  • SLH-DSA / SPHINCS+
  • WOTS+ / XMSS / FORS
  • 适合根信任、固件签名

编码密码

大公钥

基于纠错码解码难题；Classic McEliece 历史长、假设保守，但公钥很大。

  • Classic McEliece
  • HQC（NIST 备用 KEM）
  • 适合不介意带宽的场景

其他路线

有前车之鉴

多变量、同源等路线提供不同 trade-off，但安全性波动更大。

  • Rainbow：已被攻破
  • SIKE：已被攻破
  • 不要因为“后量子”就跳过审计
i

选型不是只看安全级别。 公钥/密文/签名尺寸、握手轮数、CPU、内存、侧信道、代码成熟度、协议互操作， 都会决定它能不能真正上线。ML-KEM 先上，签名后上，是更现实的路线。

03 · ML-KEM

一次 KEM，三段代码

ML-KEM 不是“加密一段消息”，而是双方协商一个 32 字节共享密钥。 下面用 CIRCL 的 ML-KEM-768 源码走一遍 KeyGen → Encaps → Decaps。

Alice 接收方

生成密钥对，保存私钥

pk = ?
sk = ?

Eve 观察者

能看到公钥和密文

pk ✓
ct ✓
ss = ?

Bob 发送方

封装一个共享密钥

pk ✓
ss = ?
1
KeyGen

Alice 生成 (pk, sk)，把 pk 发给 Bob。

2
Encaps

Bob 采样 m，算 (K,r)=G(m‖H(pk))，c=K-PKE.Enc(pk,m,r)，发 c，留下 K。

3
Decaps

Alice 解出 m'，重算 c'；比较 c==c'，相等取 K''，否则取 PRF(z‖c)。

4
Shared secret

双方得到 32 字节；Eve 有 pk 和 c，但没有 ss。

1 / 4
KeyGen：Alice 生成密钥对。公钥可以公开；私钥里的 z 用于隐式拒绝。

Decaps 的两种结果

把 ciphertext 改一个 bit，观察共享密钥是否变化、是否报错。

c == c'：ss = K''，err = nil

正常路径：重加密结果与收到的密文一致。

为什么不是“报错”？

如果 Decaps 对错误密文返回可区分的错误，攻击者就拿到一个解密 oracle。 ML-KEM 用 implicit rejection：失败时返回一个伪随机密钥， 但长度、流程都正常。

源码：Encaps 不是“加密随机数”

Bob 先采样 m，用 G(m ‖ H(pk)) 同时得到共享密钥 K 和加密随机数 r， 再用 K-PKE 加密 m。共享密钥来自哈希，不是密文本身。

源码：Decaps 先解密，再重加密

Alice 解出 m'，用同样的 G 得到 K'' 和 r'， 重新加密得到 c'。只有 c == c' 才采用 K''； 否则采用 PRF(z ‖ c)，并用常量时间选择，避免错误 oracle。

04 · ML-DSA

签名：Fiat–Shamir with aborts

ML-DSA（Dilithium）不是“哈希一下再签”。它用拒绝采样保证签名不泄露私钥信息； 一次签名可能重试多次，这是设计的一部分。

签名流程

  1. μ = CRH(tr ‖ msg)，绑定公钥和消息。
  2. ρ' = CRH(key ‖ μ)，派生 mask 种子。
  3. y = ExpandMask(ρ')，采样掩码。
  4. w = A y，分解出 w1。
  5. c = H(μ ‖ w1)，挑战。
  6. z = y + c·s1；检查 ‖z‖∞ 和 ‖w0−c·s2‖∞，不满足就重试。

尺寸

ML-DSA-65：pk 1952 B，sk 4032 B，签名 3309 B。

随机性

randomized=true 时混入 rnd，降低故障攻击与确定性签名的风险；确定性与随机化都要正确处理。

边界

拒绝采样是安全的一部分，不是“实现慢”。不要为了性能删掉范数检查。

!

签名尺寸会改变协议。 X.509 证书、JWT、固件分区、区块链交易都可能因为 3 KB 签名而超限。 迁移前先量清楚：握手、存储、MTU、日志、数据库字段。

05 · SLH-DSA

哈希签名：慢、大，但假设最保守

SLH-DSA（SPHINCS+）不依赖格；它用 WOTS+、XMSS 和 FORS 组成无状态哈希签名。 公钥很小，签名很大，适合根信任和长期固件签名。

结构

  • WOTS+：一次性签名，签一个哈希值。
  • XMSS：Merkle 树把多个 WOTS+ 公钥聚合。
  • Hypertree：多层 XMSS，减少单树高度。
  • FORS：少量一次性签名，签消息摘要。

06 · Hybrid

X25519MLKEM768：先上车，再换引擎

迁移不是“今晚把 ECDHE 换成 ML-KEM”。更现实的是 hybrid： 经典 ECDH + PQC KEM 同时跑，任何一方没被破，密钥就还安全。

组合方式

CIRCL 的 X25519MLKEM768 让 ML-KEM-768 和 X25519 各自封装， 返回 ct = ML-KEM ct ‖ X25519 ct，ss = ML-KEM ss ‖ X25519 ss。 协议层必须把拼接结果和握手 transcript 一起送进 KDF，而不是直接当密钥用。

07 · Pitfalls

PQC 的实现坑，和算法一样重要

从 RSA 换到 ML-KEM，不会自动获得安全；常量时间、密钥校验、隐式拒绝、随机性、 参数长度和组合器，任何一个出错都可能把安全性还回去。

常量时间

比较、选择、解压都不能依赖秘密分支。CIRCL 用 crypto/subtle；自己写时先问“这条分支会不会随密钥变化”。

隐式拒绝

Decaps 失败不要返回可区分错误；返回伪随机密钥，让攻击者拿不到 oracle。

密钥校验

CIRCL 的 Unpack 会检查 H(pk) 是否匹配；不要跳过反序列化校验。

随机性

用 crypto/rand；确定性 seed 只用于测试/KAT。不要用时间、计数器或 math/rand。

参数长度

ML-KEM-512/768/1024 的公钥、密文长度不同；API 必须按 scheme 分派，不能只看“都是 ML-KEM”。

侧信道

NTT、压缩、解压和内存访问都可能泄漏；CIRCL 有汇编优化，但 README 明确说不是每个包都常量时间。

组合器

Hybrid 的拼接结果要经过 KDF，并绑定 transcript；不要直接拿 64 字节当会话密钥。

审计边界

CIRCL README 明确写“experimental、无保证”。源码分析不是审计报告，生产要跟库的安全策略和版本更新。

i

一个值得记住的细节： CIRCL 的 PrivateKey.Unpack 会重新计算 H(pk) 并与存储值比较。 这不是“多余校验”，而是防止私钥文件里的公钥部分被替换后，解密/解封装行为偏离预期。

08 · Migration

迁移清单：先保密，再签名

不要等“量子计算机什么时候来”有确定答案。把迁移拆成可交付的工程步骤， 每一步都能独立验证。

1. 盘点

列出 RSA/ECC/DH 的使用点：TLS、SSH、VPN、证书、代码签名、固件、数据库字段、硬件模块。

2. 先上 hybrid KEM

TLS 1.3 用 X25519MLKEM768；保留经典 ECDH 作为后备。先解决 HNDL，不急着换签名。

3. 再做签名

从内部服务、代码签名、固件开始试点 ML-DSA；根信任/长期归档评估 SLH-DSA。

4. 量尺寸与性能

握手字节、证书链、MTU、存储、签名/验证 CPU、移动端电量；把 3 KB 签名当成协议变更。

5. 测试与回滚

KAT、互操作、负向测试、侧信道评审、灰度、回滚开关。不要一次切换全部流量。

6. 设废弃时间

给 RSA/ECC 设明确的下线窗口；监控残留流量；把 crypto agility 写进架构。

最小检查清单

  • 算法清单：知道每个 RSA/ECC/DH 用在哪里、保护什么、保密期多长。
  • Hybrid 优先：TLS/SSH/VPN 先上 hybrid KEM，保留经典算法作为后备。
  • 密钥/签名尺寸：协议、存储、证书链、数据库字段都能容纳 PQC 尺寸。
  • 常量时间：比较、选择、解压不依赖秘密；使用经过审查的库。
  • 负向测试：错误密文、畸形公钥、长度错误、重放、跨协议输入都有测试。
  • 版本固定：记录库版本/提交；PQC 实现仍在快速演进。
  • 回滚方案：算法协商失败时能退回经典算法，而不是整站不可用。
