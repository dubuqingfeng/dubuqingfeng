Agave v4.4.1 · Source Walkthrough

一笔交易写入后，
账户到底去了哪里？

AccountsDB 不是一棵每次交易都更新的全局 Merkle 树。它更像一套 按 pubkey 索引、按 slot 保存版本的日志系统： 最新状态先住进写缓存，只有 root 才追加到文件，索引负责回答“去哪儿找”。

从写路径开始
基线：5bb30402 重点：写缓存 → root 落盘 → 索引 → clean

01 · 心智模型

先记住一句话

读 AccountsDB 时，不要问“最新文件是哪个”，要问： 这个 Bank 的 ancestors 能看到哪个 slot 的哪个版本？

按 pubkey 索引、按 slot 保存版本、以追加文件为事实来源、以可重建索引回答位置。

A

事实来源

AppendVec 只追加，不原地改。账户版本以完整字节写入，旧版本不会在写入时被覆盖。

B

派生索引

AccountsIndex 记录 pubkey → [(slot, file, offset)]。它可以重建，不是账户文件本身。

C

生命周期

root 决定哪些版本可以保留、清理、收缩和进入快照。未 root 的状态只在写缓存里。

v4.4.1 的读路径是 cache-first。 主索引不再保存 Cached 条目；读账户先查写缓存，未命中才查索引和文件。

02 · 账户与 AccountsDB

pubkey 是键，AccountSharedData 是值

AccountsDB 没有一张“账户表”。它把账户拆成两半：pubkey 做键， 账户值做内容，分别放进写缓存、索引和 AppendVec。 这两半在哪里拆开、又在哪里拼回去，就是它与账户的结合方式。

AccountSharedData 里没有 pubkey。身份在键上，数据在值里；AccountsDB 负责让两者在每个平面上一一对应。

组成由谁提供在 AccountsDB 里长什么样
身份 · pubkey 交易、调用方、程序派生地址 缓存键、索引键、文件里的 StoredMeta.pubkey；不写进账户值
值 · AccountSharedData SVM 执行结果 缓存里作为值；落盘时摊平成 AccountMeta + data
版本 · slot Bank 的 slot 与 ancestors 缓存里的 slot、索引的 slot_list、文件名 <slot>.<id>
AccountSharedData执行层
pub struct AccountSharedData {
    lamports: u64,
    data: Arc<Vec<u8>>,   // clone 只加引用计数
    owner: Pubkey,
    executable: bool,
    rent_epoch: Epoch,
}

只有 5 个字段，没有身份字段。独占版本是 Account（data: Vec<u8>）； Bank 提交的写集是 (pubkey, AccountSharedData)，身份由元组的前半截提供。

为什么把键和值拆开

同一个账户值可以被多个读者共享，而 pubkey 只是查找入口。拆开之后， AccountsDB 可以原地追加整块值、在索引里只存 8 字节位置，缓存里则把键和值重新绑在一起。

代价是：任何一层都必须自己带上键。缓存用 CachedAccount { pubkey, account }， 文件用 StoredMeta.pubkey，索引用 AccountMapEntry 的 key。

同一个账户的四种形态

AccountSharedData：执行层看到的值

Bank 执行交易后产生的新账户值；pubkey 在它外面。

let writes: Vec<(Pubkey, AccountSharedData)> =
    collect_accounts_to_store(&results);

// AccountSharedData 回答“有什么”，不回答“是谁”
lamports, data, owner, executable, rent_epoch

data 是 Arc<Vec<u8>>，克隆账户值不会复制账户数据； 只有真正落盘或读回时才需要碰字节。

CachedAccount：键和值第一次被绑在一起

存在 per-slot SlotCache 里；未 root，主索引完全不知道。

pub struct CachedAccount {
    pub account: AccountSharedData,
    pubkey: Pubkey,     // 身份被显式补上
}

SlotCache: DashMap<Pubkey, Arc<CachedAccount>>

AccountsCache::store(slot, pubkey, account) 把这对键值写进该 slot 的 DashMap；同一 slot 重复写直接覆盖，只有 pubkey 首次进入该 slot 时才更新缓存内部索引。

StoredMeta + AccountMeta：值被摊平成字节

flush 时按账户整体追加；pubkey 写进 StoredMeta，是重建索引的唯一线索。

StoredMeta    48 B  { write_version_obsolete: 0, data_len, pubkey }
AccountMeta   56 B  { lamports, rent_epoch, owner, executable }
hash          32 B  全零占位（ObsoleteAccountHash）
data           N B  账户数据

stored_size = u64_align(136 + data_len)

账户值的 4 个定长字段进入 AccountMeta，data 作为变长段跟在 136 B 元数据之后； pubkey 被复制进 StoredMeta。写入时 account.pubkey() 来自 StorableAccounts，也就是元组的前半截。

StoredAccountInfo：借用文件内存的只读视图

读路径最后一步才把字节重新解释成账户值。

pub struct StoredAccountInfo<'storage> {
    pubkey: &'storage Pubkey,
    lamports: u64,
    owner: &'storage Pubkey,
    data: &'storage [u8],
    executable: bool,
    rent_epoch: Epoch,
}

索引只给 store_id + offset，文件给字节； take_account() 时才调用 create_account_shared_data， 把 data 拷成 Arc<Vec<u8>> 变回 AccountSharedData。

Account 的每个字段去哪儿了

AccountSharedData 字段大小写入哪里读回时
lamports8 BAccountMeta.lamports原值
rent_epoch8 BAccountMeta.rent_epoch原值；不参与 lt hash
owner32 BAccountMeta.owner原值
executable1 B + 7 B 填充AccountMeta.executable原值
datadata_len紧跟 136 B 固定元数据之后拷贝进 Arc<Vec<u8>>
（pubkey）32 BStoredMeta.pubkey，不是账户字段由索引或调用方给出
零 lamport 账户落盘时会被压成占位值： account_default_if_zero_lamport 让归零账户用 DEFAULT_ACCOUNT_SHARED_DATA （lamports=0、data 为空、owner 默认）写入，pubkey 仍然保留。所以“删除”在文件里依然是一条记录， 它正是后续 tombstone 的字节来源。

整体替换，没有字段级 diff

账户值以整体为单位写入：lamports、owner、data 任意一个变了，AppendVec 里就是一条完整的新记录，不会只改一个字段。

哈希只看账户值的一部分

lt_hash_account 只取 lamports || data || executable || owner || pubkey； rent_epoch 留在磁盘布局里，但不进入 bank hash。

03 · 磁盘布局

一条账户版本长什么样

AccountInfo 只有 8 字节，负责“去哪儿找”；真正的账户内容在 AppendVec 里。

account_info.rsv4.4.1
pub struct AccountInfo {
    store_id: u32,
    account_offset_and_flags: PackedOffsetAndFlags,
}

// 31-bit 逻辑 offset + 1-bit zero-lamport
const _: () = assert!(size_of::<AccountInfo>() == 8);

没有 Cached 变体。未 flush 的账户由写缓存负责。

StoredMeta 48 B write_version_obsolete / data_len / pubkey
AccountMeta 56 B lamports / rent_epoch / owner / executable
ObsoleteAccountHash 32 B 全零占位；不再保存有效账户哈希
data N B 账户数据
padding 0–7 B 对齐到下一个 8 字节边界
固定元数据 136 B · 文件上限 16 GiB · 文件名 <slot>.<id>
165 B Token 账户 136 + 165 = 301 对齐后约 304 B / 版本

每次写都复制完整 data；旧版本要等 root + clean + shrink 才真正回收。

  1. Bank 提交写集，Accounts::store_accounts 进入 SVM 账户写入。
  2. write_accounts_to_cache 反向去重；零 lamport 且无旧值时直接跳过。
  3. 账户进入 per-slot SlotCache；主索引此时完全不知道这条写入。
  4. slot 成为 root，flush_accounts_cache 只处理 rooted slots。
  5. store_accounts_for_flush：写文件 → 插入存储 → 更新索引 → 处理 reclaims。
  6. 移除缓存；后续 clean 删除旧版本，shrink 才物理回收字节。
不变量：文件先写完，索引再切过去，缓存最后移除。读者在旧缓存上失败时，可以回到索引重试。

06 · RPC 与扫描

getProgramAccounts 不是“读账户表”

它是一条服务端扫描路径：先看 ProgramId 二级索引是否可用，再用 ScanTracker 把相关 root 钉住，最后在缓存和主索引上做过滤。

1 filters 校验 最多 4 个；memcmp ≤ 128 B
→
2 ProgramId 索引？ 启用则走 index_scan_accounts
→
3 ScanTracker 注册扫描，阻止相关 root 被 clean
→
4 扫描 + 过滤 缓存与索引合并，再 owner/filter

二级索引是可选加速

启用 AccountIndex::ProgramId 时，RPC 只遍历该 program 的索引 key； 没启用则回退到全量 scan_accounts。索引启用但 key 被 include/exclude 排除时， 直接返回 KeyExcludedFromSecondaryIndex。

ScanTracker 保护扫描

扫描开始会登记 bank_id 和 max root；clean 看到正在进行的 scan 会压低 max_clean_root，避免扫描过程中把还需要读的 root 删掉。 Bank 被移除时扫描返回 SlotRemoved。

两个容易混淆的点： 索引路径有 scan_results_limit_bytes 的结果字节上限（若配置），全量扫描路径没有同样的上限； 扫描会合并写缓存，因此未 flush 的账户也可能被看到。

源码入口： get_filtered_program_accounts · scan_accounts · index_scan_accounts。 详细接口路径见 getAccountInfo 与 getProgramAccounts 源码分析。

07 · 生命周期

root 之后，旧版本怎么消失

clean 负责“逻辑回收”，shrink 负责“物理回收”；零 lamport 的删除还要跨过快照边界。

root

slot 进入 rooted 路径，flush 与 clean 才有意义。

clean

用 max_cleaned_root 收敛版本；每个 pubkey 至多保留最新 root 版本。

tombstone / obsolete

零 lamport 保留 tombstone；旧字节标记 obsolete，重建时忽略。

shrink

重写存活账户并携带 tombstone；旧文件才真正释放。

snapshot

full snapshot 推进后，才允许清掉只含 tombstone 的存储。

clean ≠ shrink

clean 更新索引、alive 计数和死字节记账；文件中间不会挖洞。shrink 才把存活账户写到更小的新文件。

零 lamport 不是立刻消失

如果账户在 full snapshot 之后归零，提前删掉字节会让增量快照丢失“归零”事实。tombstone 就是为这个边界保留的。

09 · 快照与哈希

快照不再复制文件，哈希也不再建 Merkle 树

v4.4.1 的 fastboot 3.x 用 storages list 描述账户文件；全量状态哈希改为增量维护的 AccountsLtHash。

snapshot

storages list

快照目录写 (slot, id) 列表和 obsolete accounts 文件；账户文件留在 run 目录。启动时按列表裁剪、重建、扫描生成索引。

flush storages write storages list write obsolete accounts mark loadable
hash

AccountsLtHash

1024 × u16 的格哈希，支持 mix_in / mix_out。账户更新异步计算“旧值减、新值加”，freeze 等待完成。

bank hash 混入 2 KiB lt hash；快照哈希是 checksum。

11 · 失败与边界

理解“什么时候不能相信它”

崩溃丢缓存

未 flush 的写缓存只在内存。崩溃后可以丢失并从账本重放；索引本来就可以扫描文件重建。

读到旧位置

flush、shrink、clean、purge 都可能让 store_id/offset 失效。读者必须能从索引重试。

零 lamport 跨快照

full snapshot 之后的归零不能提前彻底删除，否则增量快照恢复时旧余额会“复活”。

clean 后仍有占用

clean 只更新逻辑记账；不 shrink 的话，死字节仍占着 AppendVec。

快照哈希不匹配

启动时用扫描得到的 lt hash 校验快照；不匹配不能把状态当作可信。

版本差异

v2.2.7 的索引含 Cached 条目和 ref_count，全量哈希是 Merkle；v4.4.1 已重构，不能混用行号。

12 · 工程取舍

为什么这样设计

选择收益代价
未 root 只写缓存写入快；主索引小；未 root 分叉不污染索引读必须先查缓存；崩溃丢缓存
按 slot 追加旧版本天然支持分叉和快照写放大：每次复制完整 data + 136 B 元数据
clean 用 max_cleaned_root索引收敛，旧版本可回收tombstone/obsolete 的生命周期复杂
增量 LtHash不排序、不建树、不周期全量扫描每次更新要知道旧值；freeze 等待异步任务
storages list 快照不复制、不硬链接；启动按列表裁剪快照与账户目录生命周期耦合

AccountsDB 的核心不是“把账户写进一个文件”，而是在正确的 root 边界上，保留正确的版本，并让读路径能安全地重试。
